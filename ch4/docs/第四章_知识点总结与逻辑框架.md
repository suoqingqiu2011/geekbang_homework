# 第四章 知识点总结与逻辑框架

> **章节核心问题：** 怎样让模型每一轮拿到足够、适用、可核对的信息，并把后续任务仍然有用的知识保存下来？

## 〇、贯穿案例与学习预期

| 阶段 | 任务 | 重点观察 |
|------|------|---------|
| 修复到期边界 | 当前时间小于到期时间允许，等于或大于到期时间拒绝；不得修改现有测试，不得延长有效期绕过 | 模型是否拿到当前源码和失败证据；任务记录是否区分"建议修改 / 修改成功 / 测试通过" |
| 新会话退出登录 | 先查项目知识确认修改位置、业务规则和验证入口，再读当前源码 | 长期记忆和检索是否减少重复调查；知识能否追到来源；需求草稿是否被写成已完成功能 |
| 知识更新 | 已批准教学规则 30 → 60 分钟，但源码仍保留 30 分钟现场 | 能否分别说明"当前规则要求什么 / 源码实际做什么 / 旧版本曾经是什么" |

**掌握标准：** 能解释（各能力负责什么）→ 能追踪（沿一次任务找到材料来源、记录更新、检索候选、实际请求、回答引用和维护记录）→ 能修复并验证（发现丢约束、旧证据复用、跨项目混用、召回遗漏、引用不支持结论和更新不同步，并用反例验证）。

**参考实现（读代码找稳定职责，不把某次输出当成所有工程的统一事实）：** pi/Codex、LiteLLM、OKF/pi-okf、LlamaIndex/Milvus/BM25、LLM Wiki 实验、project3/v2。

### 六节之间的递进关系

| 顺序 | 知识点 | 解决的问题 | 前序依赖 |
|------|--------|-----------|---------|
| 4.1 | Context Engineering | 本轮给模型发什么信息？ | 无（基础装配） |
| 4.2 | Working Memory | 当前任务做到哪了？ | 需要准确的任务记录作为装配输入 |
| 4.3 | Memory | 哪些经验下次还能用？ | 当前任务结束后筛选有价值的信息保存 |
| 4.4 | RAG | 资料多了怎么找到对的？ | 保存的资料越来越多，需要检索能力 |
| 4.5 | LLM Wiki | 多份资料之间什么关系？ | 反复整理的结论形成知识页，需管理来源与更新 |
| 4.6 | 项目四 | 全部接回 Agent 执行链 | 记忆 + RAG 接回 Harness/Loop/Tool Runtime |

**一句话主线：** 装配器要选信息 → 先有准确任务记录 → 任务结束后决定留什么 → 资料多了要检索 → 整理结论形成 Wiki → 全部接回执行链验收。

## 二、各节核心知识点

### 4.1 Context Engineering：把模型每一轮需要的信息组织好

**定位：** 管理每轮实际进入模型的指令、材料、历史、工具说明和状态视图。

#### 重要环节

| 环节 | 核心要点 | 关键判断 |
|------|---------|---------|
| **Prompt vs Context** | Prompt 规定"怎样做"，Context 管理"给什么" | 指令 + 材料 + 历史 + 状态 + 工具快照，全部属于本轮输入 |
| **容量 ≠ 正确** | 上下文窗口解决"放得下"，不保证"放得对" | 信息能不能放下 / 放进去后是否适用，是两个问题 |
| **Context Packing** | 围绕下一步决策，确定直接提供、外部保存、请求中提供引用、暂缓读取的内容 | 不是全部拼接，而是有选择地装配；引用必须真实可读且位于允许访问范围内，否则不能承担恢复证据的作用 |
| **Prioritization** | 先判断有效，再分配空间 | 三问：现在还有效吗？与当前步骤相关吗？缺少它会选错动作吗？必须保留的是必要信息，不一定原文全文；分配顺序不是历史发送顺序 |
| **Budget** | 输入预算 = 上下文窗口 - 输出预留 - 安全余量 | 输出预留不能被输入借走；统计要覆盖完整请求；还要区分本轮请求预算与整个 Run 的 Token/费用/时间额度（后者由 Harness 累计） |
| **Compression** | 缩短内容，保留核对依据 | 工具结果提取关键字段，不能只截开头；长历史生成交接摘要；工具日志与任务历史使用不同压缩方法；摘要可能漏约束或把推断写成事实，关键约束由程序保留并与执行记录核对 |
| **Pollution** | 错误、过期或不适用的信息进入请求 | 过期信息 / 信息冲突 / 摘要失真 / 外部指令混入 |
| **工具消息配对** | 装配和裁剪不能破坏调用与结果的关系 | 调用 ID 合法且不重复；每条结果对应待完成调用；无孤立结果；补历史不等于重读，不能补造成功结果 |
| **超限处理** | 必须项压缩后仍放不下，就停止发送 | 精简重复规则和工具、缩小读取范围或拆步、换更小窗口的模型；不能静默删掉关键限制继续调用 |
| **Debug Report** | 查清模型实际收到了什么 | 记录每份材料的来源、处理方式、选择/排除原因；还要覆盖整个请求、运行关联、压缩过程与调用结果 |
| **Retrieval Context** | 缺什么通过工具补什么 | 依据不足 → 明确缺什么 → 补读 → 再判断 |
| **Cache** | KV Cache 复用计算，响应缓存复用回答 | 都不能证明信息正确；稳定规则保持内容和顺序一致，变化状态放后面，是否命中看实际统计；规则、权限或工具变化必须更新 |
| **成本与延迟** | 统计整个任务，而不是一个请求 | 任务完成率、总 Token、总费用、首字延迟、端到端耗时；摘要/重试/探测也计入；模型等待与工具执行分别计时 |
| **Gateway** | LiteLLM 负责路由、限流、重试 | 网关不会补回失败证据；响应缓存要让代码版本、权限和工具变化进入请求或隔离规则；SDK 与网关重试要统一管理，避免倍增；不能重放已执行的补丁 |

#### 关键公式

```
B_input = W_context - R_output - M_safety
```

#### 失败排查分流

| 现象 | 优先检查 |
|------|---------|
| 请求超出窗口 | 输入预算、工具定义、输出预留、计数方法 |
| 当前失败没进入请求 | 材料选择与装配 |
| 旧版通过记录被使用 | 证据版本与失效规则 |
| 输入充满无关文档 | 相关性与优先级 |
| 有当前证据仍答错 | 原始请求、响应与生成行为 |

### 4.2 Working Memory：把当前任务的信息组织起来

**定位：** 围绕当前任务保存目标、约束、执行事实和未完成事项的记录。

#### 重要环节

| 环节 | 核心要点 | 关键区分 |
|------|---------|---------|
| **历史 vs 工作记忆** | 历史回答"每一步发生过什么"；工作记忆回答"现在什么已完成，什么失败，什么还没做" | 历史越长、压缩越多，每轮重新推断进度越容易出错 |
| **最少保存字段** | 目标、已完成步骤、关键工具结果、未解决问题 + 约束、风险、来源、版本 | 最重要的不是字段名，而是**状态依据** |
| **三阶段严格区分** | 提出方案 ≠ 修改成功 ≠ 测试通过 | 模型建议修改 → 候选方案；工具确认成功 → 已修改；测试通过 → 对应版本的通过结果 |
| **约束与风险** | 约束是必须遵守的要求；风险是需要检查的影响 | 约束写进记忆只是帮助模型准备方案，**违规方案仍要在执行前拦住**；风险要记录依据和检查动作，更新为已排除、已确认或仍待核对 |
| **临时事实可失效** | 源码观察 / 执行事实 / 候选判断 / 修改结果 / 验证结果，性质不同 | 代码从 v1 → v2，v1 的失败仍是历史，但不能证明 v2 仍失败，v1 的通过同样不能证明 v2 正确；`status=current` 需要程序维护，写标签不会让证据永久有效 |
| **结果保存方式** | 摘要 + 原文引用，而不是整段复制 | 至少保留失败用例、输入、预期、实际、版本、执行 ID、原文位置；不能删失败断言，也不能把未测试写成通过 |
| **三类记录分工** | 执行记录 / 工作记忆 / 模型请求 | 执行记录存原始返回、调用关联、退出码和日志；工作记忆存提取后的关键结果与进度；模型请求只放本轮选中的信息；可存同一文件或数据库，但语义要能区分 |
| **工具成功 ≠ 业务通过** | 工具正常返回只说明执行完成 | 例如测试工具返回"预期 False，实际 True"，链路正常但功能仍错误；执行状态与业务断言分别记录 |
| **分支隔离** | 不同方案的代码不同 | 方案 A 与 B 不能互相用通过记录证明完成 |
| **Scratchpad** | 任务便签：计划、观察、决策、下一步 | 计划可由模型提出，执行状态必须根据真实结果更新 |
| **生命周期** | 创建 → 更新 → 保存 → 恢复 → 归档 | 保存与发送是两个动作：持久化保证能再读，装配决定模型这次看到什么；恢复要核对当前文件，归档要筛选后续有用的知识 |

#### 完整链路示例（"不得修改现有测试"）

```
1. 工作记忆保存要求及来源
   ↓
2. 装配器把要求放进模型输入
   ↓
3. Runtime 在写入前检查补丁目标
   ↓
4. Harness 根据允许/拒绝/执行结果更新进度
```

> 如果补丁涉及禁止文件，Runtime 拒绝后，记录必须变成"补丁被拒绝，代码未修改"，下一步重新准备补丁；不能沿原计划直接进入"修改后验证"。

### 4.3 Memory 体系：从当前会话走向长期复用

**定位：** 跨会话、跨任务保存并复用信息的能力。

#### 重要环节

| 环节 | 核心要点 | 关键判断 |
|------|---------|---------|
| **短期 vs 长期** | 短期服务当前任务；长期跨任务复用 | "短期"不是只能放内存，"长期"也不保证永远正确 |
| **写入前三问** | 以后哪类任务还会用到？来源能不能核对？什么变化会让它失效？ | 先筛选，再写入；凭证、令牌、密码和完整请求载荷不作为长期知识 |
| **四类信息分开存** | 要求 / 事实 / 推断 / 证据 | 要求看权限和范围；事实看版本和文件；推断只能当线索；证据用于核对 |
| **记忆生命周期** | 写入 → 检索 → 更新 → 失效/删除 | 写入后新任务必须真正读取；只看到回答提及熟悉文件名不足以证明记忆被读取，要看工具回执或确定性加载记录；更新要定位原记录，避免相似内容误覆盖 |
| **冲突处理** | 同一项目/对象/环境吗 → 来源是否适用 → 谁有权调整 → 决定替换 | 不能只因新消息更晚就覆盖 |
| **OKF 格式** | Markdown 目录树 + 顶部 YAML 元数据 + 索引 + 更新日志；`type` 必填 | 先解决知识组织，再选择检索技术；工作顺序是先读索引，再读当前任务相关概念，不必全量塞入请求；长期记忆 ≠ 向量数据库；跨项目隔离要确认存储根目录，不能只靠标签 |
| **元数据 ≠ 内容正确** | `type`、`source`、时间戳、标签只描述记录 | 不能证明每条内容已验证、能定位当前文件或存储已隔离；摘要比正文更确定，是需要核对的信号 |
| **过期 / 废弃 / 删除** | 三种不同动作 | 标为过期保留追溯但退出当前事实；废弃不再作为推荐入口；删除移除错误或不应保存的记录；删除活动记忆不自动证明备份和缓存都已清除 |
| **恢复边界** | 长期记忆不能恢复全部任务进度 | 目标、约束和步骤状态读工作记忆/Checkpoint；模块线索读长期记忆；完整日志读执行记录；当前文件必须实际读取核对 |
| **策略取舍** | 无记忆 / 完整历史 / 摘要记忆 / 按需检索 | 各有重复调查、输入增长、漏约束、查询维护成本；本项目组合方案是精确状态走工作记忆/Checkpoint、必要约定按项目读取并强制检查、经验按需检索、完整日志留引用；未做同口径比较不能宣称提升 |
| **自动记忆路径** | 启动注入目录摘要与指引 → 模型决定调用工具 → 先搜索再写入 / 先检索再读取 | "自动"指模型在指引下选择工具，不是后台无条件保存每句话 |

#### 信息性质对照

| 性质 | 例子 | 使用时怎样判断 |
|------|------|--------------|
| 要求 | 维护者规定到期立即失效 | 核对提出者权限和适用范围 |
| 事实 | 实际读取确认模块位置 | 核对版本和当前文件 |
| 推断 | 退出故障可能与缓存有关 | 作为排查线索，不能直接定根因 |
| 证据 | 命令回执、源码哈希、测试日志 | 支持核对对应结论 |

### 4.4 RAG：先找到证据，再检查回答

**定位：** 从资料中检索相关证据，放进模型输入，让模型据此回答。

#### 全链路两阶段

```
离线准备：解析 → 清洗 → 分块 → Embedding → 存储（文本+向量+元数据）
在线回答：问题处理 → 检索 → 融合筛选 → 重排/压缩 → 装配 → 生成 → 校验
```

> 数据准备先确认"读到了、关系保留、分块完整"，再调检索；没加载的文件或已删掉的条件，不会靠调高 Top-K 自动恢复。

#### 重要环节

| 环节 | 核心要点 | 常见陷阱 |
|------|---------|---------|
| **Document vs Node** | Document 是原始文档包装；Node 是分块后的检索单位 | 数量能发现漏读，不能证明正文完整 |
| **解析与清洗** | 解析要保留关系，清洗不能删掉决定含义的词 | 表格的条件与结果要绑定；PDF 保留页码、HTML 保留标题与代码块、CSV 保留列名；不能删"不得 / 仅限 / 草稿 / 旧版本" |
| **分块策略** | 规范/需求按标题；源码优先结构（AST） | 完整性高 ≠ 单位合适；块少 ≠ 效果好；分块参数是分块器的 Token 口径，不是整次请求大小；AST 不自动恢复调用链 |
| **Overlap 与元数据** | 重叠缓解边界断裂，也增加重复；元数据决定过滤与追溯 | 块数 × 窗口不是实际存储量；路径、标题、项目、行号用于引用、过滤、回源和去重 |
| **Embedding 一致性** | 文档和查询必须用匹配的模型和处理方式 | 维度相同 ≠ 不同模型的向量能比较；换模型要重建 |
| **向量存储与索引更新** | 建库与打开已有库分开 | `overwrite=False` 不等于不重复入库；要有稳定 ID、更新和删除策略；资料更新后同步分块与索引，旧分块退出当前检索 |
| **召回率 vs 命中率** | 召回率 = 每题找回的 gold 比例再平均；命中率 = 至少找到一处的题占比 | 命中率 1.0 不代表每题全部找齐 |
| **BM25 关键词** | 补精确词匹配（常量、路径、正式术语） | 中文需要一致分词 |
| **Elasticsearch 的层次** | ES 是检索系统，BM25 是评分方法 | 可以由 ES 承担关键词一路，也可以与向量库分工；用了 BM25 不等于已接入 ES |
| **Hybrid Search (RRF)** | 按排名融合，两路分数不能直接相加 | 混合不保证提升；权重与候选数来自问题集校准；RRF 的 k 是融合平滑参数，不是最终 Top-K |
| **Metadata Filter** | 对象确定以后再过滤 | 两路检索要使用相同范围与权限 |
| **Query Processing** | 术语扩展 / 查询重写 / 分解 / 多路改写 / 澄清 | 改写后要重新检索；原意不变 |
| **Rerank** | 能改排序，不能补回候选之外的内容 | 候选里没有 = 召回问题；候选有但没选中 = 排序问题；最终选中但请求中没有 = 装配问题；请求中有但回答用错 = 生成或证据理解问题 |
| **重排实际输入** | 正确来源在候选里，不代表重排模型看到了完整证据 | 保存重排实际输入；LLM 重排只给部分正文、重复编号、JSON 解析失败兜底都会影响结果 |
| **重排方式** | LLM 重排 / Cross Encoder | LLM 重排让模型对候选排序；Cross Encoder 把问题与候选成对打分，分数不是答案正确概率；本地模型可能更慢，要算上加载和候选长度 |
| **Context Compression** | 少给内容，也可能删掉证据 | 不能删掉否定、范围、版本和条件 |
| **后处理取舍** | 同时看质量与开销 | 重排可能减少无依据实体，压缩可能省输入但增加等待；最终输入变短不等于总费用降低；比较延迟要固定起止范围，不能把包含最终回答的两段直接相加；8/8 关键词检查不是全面正确率 |
| **Citation 三层检查** | 编号合法 → 实体核对 → 结论支持与完整性 | 编号合法 ≠ 证据支持结论；一致性检查是本项目应用层规则，不是框架自动保证；30 分钟 = 1,800 秒只是换算，不能证明当前代码常量 |
| **校验失败后的发布** | 校验结果要定义发布行为 | 证据不足可拒答或标缺口；引用越界修复后重检；重要结论不受支持不发布确定答案；流式输出要先检查后发布或标注待校验 |
| **评估口径** | 固定问题集，同口径比较 | 一次尽量只改一个变量；V0–V3 比较整套配置，不能把多处变化归因给单一算法；组件增加不是提升证据；失败归因先看是否有任意 gold 进入结果，无 gold 为检索失败，有 gold 且答案检查失败才标生成失败；无答案题单独统计，未知 usage 不填 0 |

#### 失败排查六步定位法

```
1. 原文是否有答案，状态是否适用？    → 补来源或说明缺口
2. 解析与分块是否保留关键条件？     → 加载、清洗、分块、元数据
3. 候选中是否有答案证据？          → 查询、模型、分词、过滤、召回
4. 最终节点和请求是否保留？        → 重排、压缩、预算、装配
5. 回答结论是否受引用支持？        → 提示词、生成、结论核对
6. 检查结果是否如实表达覆盖？       → 标注、检查器、发布规则
```

### 4.5 LLM Wiki：把整理结果变成可维护的知识资产

**定位：** 模型根据原始资料生成、组织和维护知识页，保存可复用的总结、关联和分析。

#### 最小目录与治理文件

| 位置 | 用途 | 修改规则 |
|------|------|---------|
| `raw/` | 原始资料版本快照 | 不由模型改写，新来源新增快照 |
| `staging/` | 未通过发布检查的草稿 | 可修改，不能默认作为现行依据 |
| `wiki/` | 检查后发布的知识页 | 按发布规则更新 |
| `schema.md` | 来源、版本、冲突和权限规则 | 由工程师明确规范 |
| `manifests/` | 来源清单、哈希与页面依赖 | 与页面版本同步 |
| `logs/` | 生成、校验、发布和失败记录 | 保留实际操作事实 |
| `reports/` | 影响分析、巡检与验收 | 写清证据和未验证项 |

> 先准备规则、来源和空索引，不等于已经生成或发布知识页。

#### 重要环节

| 环节 | 核心要点 | 关键原则 |
|------|---------|---------|
| **Wiki / RAG / Memory 分工** | 工作记忆接着完成任务；长期记忆召回模块与经验；Wiki 阅读整理后的规则、实现和验证关系；RAG 为当前问题找原文或知识页 | Wiki 维护知识，RAG 为本次问题找到知识；可以先检索 Wiki，再沿引用核对原文 |
| **工作模式** | LLM Wiki 把部分阅读、提取、补链接和更新工作交给 Agent | 不是装上就自动成立；需要用户指令或调度触发；版本、审核、来源和权限仍由工程师规定 |
| **知识页三问** | 适用于哪里？结论是什么？依据在哪里？ | 页头管理身份/版本/状态/来源；正文组织规则/实现/核对入口 |
| **需求与实现分开** | PRD 提出退出登录，当前 `logout()` 仍抛 `NotImplementedError` | 页面分别写需求目标和源码状态；不能把"希望实现"写成"已经上线" |
| **生成与发布分开** | 模型输出正文 + 结论到证据映射 + 待核对事项；程序控制提交 | 先固定合法输入，再生成草稿；程序查结构，内容核对查含义 |
| **提交前再检查** | 生成期间可能原文更新、身份撤权、别人修改同一页 | 再次核对来源哈希、权限和页面基线 |
| **来源追踪** | 整页参考资料不够，关键结论要具体对应 | 派生页也要追到原文；重要结论可直接引用原文 |
| **来源清单** | 登记 source ID、相对路径、实际 SHA-256、资料类型和原文日期状态 | 原文没写的信息记未知；不能把本次导入版本当成资料业务版本 |
| **问答归档** | 有复用价值的问答可以归档 | 先核对来源、范围和重复；已有同类页优先更新；没有证据的猜测列待研究；不把模型输出自动变成事实 |
| **来源更新** | 沿依赖传递，不能全局替换数字 | 先登记新快照 → 找直接/间接影响 → 标待复核 → 重读更新；未同步期间当前规则查询可回到新原文，并说明 Wiki 待更新，不能无提示继续使用旧页 |
| **索引与缓存同步** | 来源更新沿页面、分块、检索索引、摘要和缓存传播 | 页面保留稳定身份，内容用版本区分；同步失败要标状态并回退当前原文；没接索引或缓存就标未接入，不能声称已同步 |
| **重复/过期/冲突** | 三种不同动作，不是一个处理方式 | 重复合并、过期退出当前使用、冲突比较范围与权威 |
| **巡检** | 检查重复页、旧规则、冲突、孤立页、坏链接和依赖遗漏 | 报告先列页面、问题、证据、影响与建议，不直接删除或合并；"本次未发现问题"不等于永久正确 |
| **权限贯穿全流程** | 来源读取 → 生成 → 发布 → 使用 → 撤权 | 最小整页方案：读者满足所有来源的访问条件，才可读该页；公开介绍单独用公开来源生成，受限内容对外使用按规定脱敏与审批；撤权要沿依赖调整页面权限，并使索引、摘要、缓存和相关长期记忆失效；有权限机制就测试真实拒绝，没有就如实标未实现，不伪造拒绝日志 |
| **权限不是字段** | `access_policy` 字段和提示词不是鉴权 | 搜索有权限检查、`read_file` 没有，也会形成绕过；要从多个入口验证同一限制 |
| **四维质量验收** | 完整性 / 可信度 / 时效性 / 可检索性 | 程序检查结构，模型辅助检查语义；只有索引导航就记录导航结果，不虚报召回率 |

#### 关键示例：60 分钟规则更新

必须能分别回答这些层次：

| 信息层次 | 示例表达 |
|---------|---------|
| 当前已批准教学规则 | 登录 60 分钟，请求触发续期 |
| 原始源码实际行为 | 若仍为 1,800 秒，说明实现还是 30 分钟 |
| 历史记录 | 保留当时 30 分钟 |
| 未批准建议 | 90 分钟属于讨论建议，不能覆盖现行规则 |

**不能全局替换 30 或 1800。**

### 4.6 项目四：给 Codebase Agent 装上记忆和检索

**定位：** 把长期记忆与 RAG 接回 project3/v2，沿真实执行链验收；不新增绕过治理的执行路径，也不把检索答案直接当成代码已修改的结果。

#### 五大验收目标

| 目标 | 要证明什么 | 通过依据 |
|------|-----------|---------|
| **找得到** | 新会话能取得相关记忆，RAG 能找到回答证据 | 读取或工具调用记录，相关来源进入请求 |
| **装得下** | 新增内容仍通过本轮输入预算 | 总请求受控，关键证据保留，必须项超限停止 |
| **记得准** | 要求、事实、推断、来源和版本不混用 | 性质与范围明确，不直接当当前事实 |
| **恢复得了** | 当前任务进度能恢复，旧证据经现场核对后使用 | 找回状态，核对现场，继续当前版本验证 |
| **解释得清** | 回答和操作能追到记忆、资料、源码与执行记录 | 引用编号、原文位置、版本和 Trace 对应 |

#### 六处接入（长期记忆）

| 位置 | 作用 |
|------|------|
| `config/platform.yaml` | 增加记忆开关与配置，平台能明确启用或关闭 |
| `src/memory.ts` | 实现 list / search / read / remember / digest / validate，负责文件组织、读写与校验 |
| `src/tools/memory.ts` | 暴露 `memory_recall` 与 `memory_remember` 两件工具 |
| `renderSystemPrompt` | 运行前读取配置的长期记忆摘要，让本次运行得到相关知识入口 |
| `config/prompts.yaml` | 在 `codebase.agent` 中补"先召回、核对、再应用"的使用规则 |
| `tests/unit/kg_memory.test.ts` | 覆盖持久化、索引、召回与边界测试 |

> 文件名以实际工程为准，重点是六类职责。单元测试至少覆盖：remember 写入合法 OKF、index/log 同步、recall 按 query 和 ID 找回、路径穿越在写入前被拒绝、新进程能读到持久记录；还要检查拒绝或未批准不写入、错参数不执行 handler、记忆开关关闭时行为符合配置。
>
> 记忆内容是项目材料。即使模板把材料追加到系统提示词，也不能让外部记忆里的指令覆盖可信规则。

#### 接入要点

| 接入对象 | 关键要求 |
|---------|---------|
| **memory_recall** (read) | 按 query 或 ID 找回记忆，走 Tool Runtime；与仓库工具一样经过白名单、RBAC、参数契约和审计 |
| **memory_remember** (write) | 写入合法 OKF 概念并同步 index/log；属于持久副作用，需审批，批准只针对对应写入 |
| **rag_query** (read) | 只读查询，仍需 RBAC；输出 = 回答 + 编号来源追溯；`[n]` 要与来源逐条对应 |
| **启动加载** | 运行前读取长期记忆摘要，具体结论读全文和当前源码 |

#### RAG 先独立验证，再接成只读工具

- `ingest.py` 负责资料入库，建立向量与 BM25 索引；`query.py` 提供查询模式、Top-K、生成开关与 JSON 输出。
- 首次或资料更新后入库；日常查询使用已有存储，避免每次重复向量化整套资料；`--overwrite` 只用于明确重建，执行前确认目标。
- 先确认索引、答案和引用正确，再接 Agent；失败时才能分清是后端检索问题，还是工具适配与结果回写问题。
- 示例使用 BGE 中文本地向量（512 维），不沿用第一步 MiniMax 的 1536 维配置。
- `--json --no-llm` 只观察检索结果和引用，不能把它说成已经由回答模型综合生成结论。

#### 验收看证据，不看"答案里有没有 30 分钟"

- 用 Trace 证明模型本次实际调用了 `rag_query`；只看最终回答不够。
- 如果没调用，先检查工具快照、使用指引、启动注入和实际请求，不能伪造工具记录。
- 完整链路：用户问题 → 模型调用 → Runtime 校验与授权 → RAG 后端结果 → 编号格式化 → 下一轮输入 → 最终回答。

#### 冲突时的处理原则

```
RAG 规则写 30 分钟，源码实际计算为 20 分钟
    ↓
先指出差异，再读取当前规则、代码和测试
    ↓
判断是：记忆过期 / 资料滞后 / 实现不符合规则
    ↓
源码说明现状，规则说明目标，测试验证指定版本行为
```

> 不能以更新文档掩盖代码问题，也不能让源码自行改写已批准的业务要求；历史记忆只证明过去核对过的事实或经验，不能直接当当前现场。修复代码仍需用户目标、当前证据、授权和修改后测试。

#### 主动制造反例

1. 未批准写记忆：没有概念文件写入。
2. 路径穿越：Runtime 或记忆模块拒绝，目标外文件不变。
3. 新会话：不继承旧聊天，仍能实际取得持久记录。
4. 资料更新：旧规则不继续作为默认当前答案。
5. 资料与源码冲突：回答保留差异，不假装已经一致。
6. 引用编号错位：格式或检查失败，不宣布可追溯性通过。
7. RAG 或记忆失败：结构化错误进入下一轮，不伪装成空结果成功。

## 四、工程师 vs AI 分工总结

| 工作 | AI 可以辅助 | 工程师必须核对 |
|------|-----------|--------------|
| 信息结构与模块边界 | 编写模块和接口 | 数据样例与真实链路 |
| 上下文与记忆策略 | 实现装配、压缩和存储 | Debug Report、更新与恢复结果 |
| 检索方案 | 接索引、混合与重排 | 固定问题集的对照结果 |
| 来源、版本与权限 | 实现过滤和维护 | 引用核对、版本与拒绝用例 |
| 最小规格与验收 | 编码、补测试和修复 | 测试报告、Trace 和失败分析 |

## 五、本章六条核心判断

1. **Context Engineering** 的核心是本轮需要的信息确实进入请求，而不是材料越多越好。
2. **Working Memory** 的核心是状态符合执行事实，不能把建议当完成，把旧测试当当前验证。
3. **长期记忆** 的核心是后续任务能够取得仍适用的知识，保存后还要读取、核对和维护。
4. **RAG** 的核心是正确证据进入候选和实际输入，再检查模型是否正确使用。
5. **LLM Wiki** 的核心是整理结果能够追溯、更新和受控使用，文件保存只是起点。
6. **项目四** 的核心是记忆和检索接回同一治理链，并用真实调用、来源和执行结果验收。

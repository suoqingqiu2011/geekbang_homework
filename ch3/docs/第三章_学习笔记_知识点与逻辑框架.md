# 第三章 学习笔记 · 知识点整理与逻辑框架

> 主题：**从单步工具调用到可恢复的长程 Agent**
> 一句话主线：第二章给了 Agent 一只"受控的手"，第三章要给它**能持续推进、能记住做到哪、能中断后接着做、能被边界约束、能被装配成整机**的一副身体。

---

## 一、全章逻辑框架：七节是"七层"，不是七个并列知识点

```

                              │
                              ▼

│                                                                      │
│  ① 推进  3.1 Agent Loop      下一步依赖上一步产生的新事实                │

│     ▼                                                                 │

│     │        产出：PlanStep / Evidence / readySteps / 原子修订           │
│     ▼                                                                 │
│  ③ 时间  3.3 State+Checkpoint 九态状态机 + 执行记录 + 存档 + 恢复五步      │

│     ▼                                                                 │

│     ▼                                                                 │

│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

**纵向读法（能力叠加）**：每一节解决上一节留下的"新漏洞"。

| 上一节留下的问题 | 下一节怎么补 |
|---|---|
| Loop 能跑，但容易忘记目标、说不清还差什么 | Planning：把目标拆成带完成标准和依赖的子目标 |
| 有计划，但进程一断就只剩聊天记录 | State/Checkpoint：把计划、证据、审批、预算存成可核对存档 |
| 能恢复，但一旦真的读写文件和跑进程就可能不可挽回 | Sandbox：路径、命令、网络、时间四维边界 |
| 各模块都正确，但接起来就漏、就错、就重复 | **Harness：管装配与状态一致性（本章枢纽）** |
| 装配能跑，但多分支、长等待、循环难以检查和可视化 | LangGraph：把流程显式表达成状态与迁移 |
| 机制都懂，但没有真实任务闭环 | Codebase Agent v2：两类仓库任务验收 |

**横向读法（同一事实贯通）**：全章真正的统一命题是——

> 一次工具执行产生的事实，必须**同时**正确到达四的地方：模型上下文、业务状态、审批/审计、完成检查。任何一处缺失或错版，都会表现为"看起来完成了"。

这就是 Harness 一节的核心，也是后面所有反例的通用诊断入口。

## 二、贯穿全章的两条验收任务

| 任务 | 提示词 | 考什么 |
|---|---|---|
| 代码理解 | 找出项目登录逻辑并生成 Markdown 说明 | 搜索、阅读、引用真实路径、交付物落盘 |
| 测试修复 | 读失败测试与日志，修复源码并复测，不改现有测试 | 复现、计划、补丁、三组测试、失败分析、状态恢复 |

**三层掌握标准**（全章通用，也是最后项目验收标准）：

1. **能解释**：Loop / Planning / State / Sandbox / Harness / LangGraph 各自负责什么。
2. **能追踪**：沿一次任务找到 输入 → 决策 → 校验 → 执行 → 回写 → 完成检查 → 恢复入口。
3. **能修复并验证**：发现"绕过 Runtime、旧证据复用、旧审批复用、写操作误重放"，并用测试证明修复有效。

**本章参考的四类实现**（读源码的目标是提炼稳定边界，不是照搬）：

| 参考实现 | 重点观察什么 |
|---|---|
| pi | Agent Loop、事件、Hook、会话续接、中断信号、工具适配 |
| Messages API | 手写 Harness 时，消息配对、状态回流、门禁与宿主批准由谁完成 |
| LangGraph | 状态图、条件边、ToolNode、interrupt、Checkpoint、可视化 |
| project3/v2 | 十件仓库工具、两类任务、Sandbox、审批、审计与评估的完整组合 |

**AI 可外包 vs 工程师必须把关**：AI 适合生成 Schema、适配代码、异常分支、测试样板、节点与条件边、验收脚本；但"用哪种执行方式、什么算完成、哪些必须审批、计划该不该修订、中断后哪些进度可信、边界放在哪一层、会不会重复副作用"必须由工程师判断。

## 三、分节知识点与关键环节

### 3.1 Agent Loop —— 让任务能继续

**核心命题**：复杂任务需要 Loop，不是因为步骤多，而是因为**下一步依赖上一步产生的新事实**。

**关键环节**

| 环节 | 要点 | 反例/坑 |
|---|---|---|
| 控制权上移 | 从"逐轮提示"变成"设计触发、反馈、验收、停止系统" | 只加 while，把风险放大几十倍 |
| LoopEngine 五件事 | 组装 Context → 调模型 → 分发 Tool Call → 回写 Tool Result → 决定继续/结束 | — |
| 结果回写 | 历史必须同时保留 Tool Call 和对应 Tool Result，观察—行动才闭合 | 只 print 到终端，模型没看见结果 |
| Turn / Run | Turn = 一次模型响应 + 它提出的 0~N 个工具调用；Run = agent_start→agent_end | 把"用户问一次"当"模型只调一次" |
| 适用条件 | 目标清晰、结果可验证、过程可收敛 | "把 UI 做得更好看"不适合自主 Loop |
| 两层循环 | 任务内（runAgentLoop）/ 任务外（触发、定时、事件） | 把定时任务、Sub-agent、Memory 全塞进"Agent Loop" |
| 五个对象分工 | Function Calling / Tool Runtime / Agent Loop / LoopGuard / Harness | 概念混用，代码说不清谁管什么 |
| ReAct vs Plan-Execute | ReAct 回答"这一步往哪走"；Plan-Execute 回答"整体怎么走"；二者可嵌套 | 重复同一搜索还宣称"新一轮分析" |
| 完成契约 | 返回**缺失项列表**而非布尔值，Host 可转成 Follow-up | 模型说完成就交付 |
| 最大轮数 | maxTurns、时间、Token、费用；Follow-up 不清零计数 | 只有验收没有预算 |
| 停止可解释 | 完成 / 等待用户 / 主动停止（预算、取消、权限、不可恢复错误） | 把"停止"当"失败"或当"成功" |
| 死循环识别 | 动作指纹 = 工具名 + 规范化参数（canonicalJson 递归排序）哈希 | 相同动作一定是死循环 |
| 真进展判据 | 文件版本、测试结果、已验证事实、计划推进、错误原因是否变化、A/B 振荡 | 只看"有没有输出" |
| 中断 | AbortSignal 贯穿模型/Hook/工具/子进程；中断 ≠ 回滚 | 只停界面输出，测试进程还在跑 |
| 事件序列 | agent_start → turn_start → message_start/update/end → tool_execution_start/end → turn_end → 下一轮或 agent_end；用于 Trace、UI、Checkpoint、人工接管 | 只有 while，没有可观察的运行边界 |
| steering vs followUp | steering 在当前轮与工具处理结束后的安全边界注入，影响后续决策；followUp 在循环准备停止时接着处理；两者都不是定时调度 | 把中途补充指令当成新任务，或与任务外循环混为一谈 |
| 工具执行前后 Hook | beforeToolCall：找工具、兼容参数、校验 Schema、Run 级重复保护（权限仍由 Runtime 判定）；afterToolCall：截断、脱敏、标记错误、提取证据 | 把权限判断塞进 Hook，或在 Hook 里吞掉错误 |
| 批次语义 | 准备失败会形成错误 Tool Result；只有整批最终结果都标记 terminate:true 才提前结束；并行执行也按原 Tool Call 顺序回写 | 单个工具设置终止就认为整批结束 |
| LoopGuard 四项控制 | beforeToolCall 指纹去重 / afterToolCall 提取证据 / afterTurn 检查轮数与完成证据 / drainFollowUps 注入下一轮 | 让 Guard 顺带管计划、状态机与持久化 |
| 工具适配四条不变量 | toolCallId 不丢失；模型参数仍属不可信输入；所有工具进同一个 invoke()；Tool Result 先治理再进 Context | 在适配层另开一条绕过 Runtime 的路径 |
| 本节四个工具 | list_files / search_code / read_file / write_file（只允许写 artifacts/） | 过早开放通用 run_command |
| 完成契约的最低门槛 | 示例：读文件数 < 3 或缺 artifacts/login-flow.md 即返回缺失项，由 Host 转成 Follow-up；最低门槛不等于完整业务验收 | 把"读三个文件"当作读对了 |
| 脚本化验收 | 下轮 Context 含上轮 toolResult 且 ID 匹配；缺证据 FINAL_REJECTED；第三次 REPEATED_ACTION；到顶 MAX_TURNS_EXCEEDED；取消 aborted；真实集成至少一次 Tool Call → Result → 下一轮 | 只看最终文档，分不清"真探索"与"训练数据猜" |

**本节验收（关键断言）**：第二次模型调用的 Context 必须包含上轮 toolResult 且 ID 匹配；第三次相同动作 handler 只执行 2 次并返回 REPEATED_ACTION；模型调用次数恰等于 maxTurns。

### 3.2 Planning —— 让系统知道做到哪一步、还差什么

**核心命题**：Loop 保存的是"读过什么、说过什么"，Planning 补的是"任务还差哪几步、哪一步的结论作废了"。

**关键环节**

| 环节 | 要点 |
|---|---|
| 何时需要计划 | 需要持续追踪多个子目标、依赖、验收时才加；单次查询、固定规则、制度固定流程、低延迟、高风险锁流程 → 不需要 |
| 四种执行方式 | 直接 Tool Calling / 固定 Workflow / Agent Loop / Loop + 显式计划（可混用） |
| 一次性 vs 动态计划 | 一次性 = 模型临时列步骤；动态 = 只定"先查清—再修—再验"，证据驱动修订 |
| 动作 → 可验收结果 | 每步问两句：做完拿到什么？拿什么证明？（复现失败 = scope=target 退出码 1 + 断言期望/实际） |
| 计划三对象 | Plan / PlanStep / Evidence |
| PlanStep 字段 | id、objective、dependsOn、successCriteria、status、evidenceIds、attempts、lastError |
| Evidence 字段 | id、stepId、toolCallId、**artifactVersion**、kind(tool/test/diff/inspection)、summary、payload |
| Plan 级字段 | id/version/objective、constraints（保存约束，实际限制仍由执行检查落实）、maxRevisions、steps、修订历史 |
| 标准与证据分离 | successCriteria 事前定义，evidenceIds 事后记录，不能混 |
| 六种依赖 | 前置 / 数据 / 权限 / 验证 / 汇合 / 互斥选择 |
| readySteps | **由程序计算**，不由模型声明；依赖就绪 ≠ 无资源冲突（同文件不能贸然并行） |
| skipped ≠ completed | 跳过验证步骤不能算通过；必须先说明原因并改接依赖 |
| 偏差分流 | 参数错→改参数；路径变→局部修正；超时→受控重试；假设被推翻/新约束/结构变化→修订；权限拒绝、预算耗尽→记录阻塞，不能靠改计划绕过 |
| 失败分类 | assertion / environment / timeout / infrastructure（非零退出码本身不够，缺依赖≠复现成功） |
| 一次修订的六项检查 | 版本对齐（expectedVersion）→ 修订预算（maxRevisions）→ 依据（reason + 真实 evidenceIds）→ 候选副本上应用 → 整体校验（ID 唯一、依赖存在、无环）→ 提交（版本+1、计数+1、追加记录） |
| 修订只改路径不改标准 | 不能把"回归通过"改成"运行过回归"；用户加约束要检查已有 Diff 并让冲突步骤失效 |
| 计划门禁位置 | 在 handler 之前；planStepId 检查后、进 Runtime 前要**剥离** |
| 组件分工 | Planner 提子目标、依赖与修订建议；PlanStore 存步骤/状态/修订史并检查依赖转换；Verifier 判断证据是否满足验收；Runtime 管参数、权限、超时；pi 继续负责循环 |
| StepStatus 六值 | pending / in_progress / completed / blocked / skipped / failed，不能只有完成与未完成两值 |
| 完成某一步前的四项检查 | 证据非空 → 引用证据存在 → stepId 一致 → test/diff 类证据版本等于当前代码；四项只回答"证据拿对没有"，够不够满足标准由 Verifier 判断 |
| 两层验收 | 步骤验收（StepVerifier）决定这一步算不算完成；任务级 CompletionContract 决定整体能否交付；步骤全勾上不等于任务完成 |
| 有无计划的同一任务对照 | 8 轮 vs 17 轮：多花的轮数换来 s1–s6 六个步骤、每步状态与关联证据——买的不是速度，是可检查的进度记录 |
| 六步修复计划 s1–s6 | 定位入口与范围 → 复现失败（scope=target 退出码 1）→ 按证据确认根因 → 最小受控 Diff → target/boundary/regression 全 0 → 交付说明（一步可含多条证据） |

**一句话收束**：子目标给出完成标准，依赖决定执行顺序，观察推动修订，证据决定能否交付。

### 3.3 State Machine 与 Checkpoint —— 让进度能跨进程恢复

**核心命题**：能继续对话 ≠ 能恢复现场。会话记录恢复"聊过什么"，业务恢复要恢复"哪一步可信、哪次写入结果不明"。

**关键环节**

| 环节 | 要点 |
|---|---|
| 会话持久化边界 | `-c`/`--continue` 续接最近会话；`-r`/`--resume` 打开会话选择器；`--session-id` 指定项目会话；`--fork` 派生新会话（只复制会话，不还原工作区）；`--session-dir` 指定存档目录；`--no-session` 关闭持久化 |
| 存档为何会失真 | 补丁写入 → 更新内存版本 → 工具返回 → 轮次边界存档，中间有空当；"存档没记录"≠"动作没发生" |
| 中断语义 | 同一 AbortSignal 不可复位；能否及时停取决于执行环节是否支持取消；断电无法保证收尾；中断不是回滚 |
| 业务必存四类 | 计划与步骤进度 / 工具执行记录与证据 / 工作区标识与内容摘要 / 待审批动作与人工决定 |
| 四个接入位置 | beforeToolCall（放行/拦审批）、afterToolCall（补记录）、事件订阅（转业务状态）、续跑接口（恢复后继续） |
| 九个任务状态 | created / planning / running / waiting_tool / tool_failed / waiting_approval / completed / failed / cancelled |
| 两个易混点 | 工具失败 ≠ 任务失败；暂停（running + INTERRUPTED）≠ 取消（cancelled） |
| 步骤执行记录 | 属于哪步、什么工具、什么参数、toolCallId、结果或错误、失败后决策、重试与预算 |
| 结果不明 | "工具返回未应用"=已知失败；"发起后进程退出"=结果不明，不能写成失败后可重试 |
| Checkpoint 内容 | 目标与约束、计划与修订史、执行与不明结果、工作区版本/摘要、待审批、剩余预算、会话引用 |
| 保存时机 | 完整轮次后 + 准备等待审批前；不能只在退出时保存 |
| 原子写 | 临时文件 → 替换；带格式版本 + 校验和；保存失败要停止推进并保留上一份有效存档 |
| **恢复五步** | ①存档可用（可读/格式/字段/校验）→ ②现场核对（目录、文件、不明操作）→ ③业务是否允许继续（completed/cancelled 不续跑，审批不能因重启被绕过）→ ④还原业务对象 → ⑤再调续跑 |
| 停止的三层区分 | 已请求停止 / Agent 不再发起新操作 / 已启动的操作确实结束 |
| 停止记录 | 已确认完整执行 → 恢复真实结果；确认未执行 → 满足条件再执行；部分或不明 → 保留未决，交人处理 |
| afterToolCall 的 terminate 语义 | pi 会检查整个工具批次，只有所有最终结果都设置终止提示才提前结束 |
| 续跑接口 | runAgentLoopContinue / agent.continue()；调用前先还原计划、证据、审批状态与运行计数，并完成工作区校验 |
| 格式版本 ≠ 代码版本 | 格式版本描述存档结构（当前程序能否读）；代码版本描述工作区内容；可选字段统一省略或统一写 null |
| 三个验收场景 | ①中断后接上进度（诊断完成、补丁未执行、计数保留）②审批前拦住补丁（文件未被提前修改，批准/拒绝两路都验证）③失败后可对照（独立工作区，两次记录可查阅） |

**核心句**：Checkpoint 的作用是为恢复提供依据；**真正决定能否继续的，是存档检查 + 现场核对 + 业务规则**。

### 3.4 Sandbox —— 把影响限制在可拦截、可审计、可恢复的范围内

**核心命题**：边界要防的不是"出错"，而是**不可挽回**。前三节控制"循环怎么走"，本节控制"每一步能碰到什么"。

**关键环节**

| 环节 | 要点 |
|---|---|
| 三个必须接受的事实 | ①模型输出（含**意图**）永远不可信；②读到的内容本身可能是攻击（README/注释/网页注入）；③Loop 是风险放大器 |
| 三个目标 | 可拦截（执行前拦下）、可审计（含被拦下的）、可恢复（损失有上限） |
| 两条原则 | 默认拒绝（白名单，黑名单枚举不完）；越界可感知（不静默失败） |
| 文件三区 | 只读区（源码/文档）、可写区（artifacts/、临时）、禁止区（~/.ssh、~/.aws、.env*、*.pem、*.key、系统目录 → **硬阻断，不走审批**）；可写区隐含可读 |
| 读写强度差异 | 读错泄露信息，写错不可逆 → pi-sandbox：denyRead 可触发授权，denyWrite 硬阻断 |
| 路径校验 | 必须 **resolve 后**比较前缀，且**带目录分隔符**；三个坑：`..` 逃逸、`/repo/artifacts-evil` 前缀冒充、软链接（realpath 或禁链） |
| 边界集中化 | 写进 ExecutionContext（repoRoot / artifactRoot / targetArtifact / targetSource / targetSuite / boundarySuite / regressionSuite），可注入可覆盖；逐文件白名单 |
| Shell 最危险 | Shell 是所有工具的超集：`read_file(~/.ssh)` 被拒，`cat ~/.ssh` 就绕过去了 |
| 专用工具优先 | 能提供 `run_test(scope)` 就不要开 `run_command`；模型没有机会注入命令串 |
| 命令三级 | 只读观察（git status/ls/grep）→ 可逆修改（npm install/git commit）→ 不可逆/外发（git push、rm -rf、curl、sudo、管道到 sh）→ 拦截或审批 |
| 解析层拦截 | 拆成 命令头 + 参数 + 重定向 + 管道 逐段检查；正则会引号/转义/变量替换绕过；拦截必须发生在执行前 |
| Shell 四维 | 路径、命令、网络、**时间与输出量** |
| 超时 | 默认 30s；真杀进程组（含 fork 子进程）；与 AbortSignal 打通；长输出只回尾部+退出码，全量留审计 |
| 结果不明落地 | run_test 启动前先登记"已启动、结果不明"，拿到退出码才销记 → TEST_RESULT_UNKNOWN |
| 网络三类 | 外网域名白名单（禁止 `*`）、内网默认禁止（防横向移动与元数据服务）、第三方 API 用网关凭证（Agent 不持真实密钥） |
| 环境变量 | `run_command("env")` 一句话泄露；只注入任务必需变量 |
| 两种 Sandbox | 本地：共享宿主、零冷启动、隔离弱；Docker：一次性替身、干净环境、需镜像与回传产物 |
| 审计日志 | append-only JSONL：runId/turn/toolCallId、tool+参数摘要、decision+命中规则、actor、resultCode/duration、artifactRef |
| 审计与 Checkpoint 分工 | Checkpoint 回答"从哪继续"（轮次边界/审批前）；审计回答"发生了什么、谁放行的"（每次调用含拦截）；用 runId + toolCallId 关联 |
| 风险回放 | 误拦 / 漏放 / 越权尝试；五步：定位 toolCallId → 还原 decision 与规则 → 沿 runId 追溯意图来源 → 修防 → 写成回归场景 |
| 最小规格 R1–R6 | 文件三区分级 / Shell 白名单与高风险拦截 / 网络域名白名单与凭证最小化 / 超时与取消 / 审计留痕 / 回放能力 |
| 本节验收 A1–A6 | 路径逃逸被拒且有 deny 审计；危险命令 handler 执行 0 次；白名单外命令批准前不执行；超时真杀进程组；白名单外域名被拦且 env 无宿主变量；仅凭审计可还原轮次/工具/参数/规则 |
| Sandbox 选择 | 交互式开发、可信仓库 → 本地；陌生仓库、第三方 install、夜间批处理、并行 Agent、强隔离合规 → Docker；常见做法是组合：策略层共享，隔离方式按风险选 |

**验收铁律**："该失败的必须失败"；**拦截的证据是 handler 没执行，不是返回了错误**。

### 3.6 LangGraph —— 显式编排分支、并行、人工中断与循环

**核心命题**：LangGraph 的价值不是"Agent 一定要画图"，而是当流程复杂到需要把状态与迁移显式化时，图比散落的条件分支更好检查。

**关键环节**

| 环节 | 要点 |
|---|---|
| 生态边界 | LangGraph 管编排；LangChain 提供模型客户端/消息；LangSmith、Langfuse 只观测不恢复；Dify 面向业务可视化；AgentScope 另一套多 Agent 框架 |
| 两条铁律 | Trace 记录"发生过什么"，Checkpoint 保存"接下来怎么继续"；用 LangGraph 不必装 LangChain 全家桶 |
| 对象映射 | 工单=State；步骤=Node；依赖=Edge；总装=StateGraph；等待=interrupt+Command(resume)；跨进程=Checkpointer；工具=ToolNode |
| State 声明 | TypedDict（运行时不拦额外字段）+ NotRequired |
| 节点增量 | 节点只返回自己改的字段，框架合并；并行/重跑/存档决定必须"报增量" |
| compile | 做结构检查（孤立节点、缺边），不检查业务规则；即使 P1 也先挂 Checkpointer |
| 条件路由 | add_conditional_edges(source, path_fn, path_map)；路由只读 State；返回 `Literal[...]` 才能让 Mermaid 显示分支标签 |
| ToolNode | 只看 messages 末尾 AIMessage，按 tool_calls 并发执行 → 追加 ToolMessage；必须是**一个节点内部并发** |
| Reducer | 多节点写同一字段的合并规则；messages 用 add_messages（按 ID 追加去重），approvals 用 add（累加审批） |
| interrupt 心智模型 | 不是"停在这一行等"，而是"这次执行到此为止，下次从头再来这一行"；保存的是 State，不是调用栈 |
| **绝对规则** | `interrupt()` 之前不能有任何副作用；流程应为：前一个节点生成补丁写入 State → 审批节点只展示收决定 → 审批后独立节点真正写入/部署 |
| Checkpointer + thread_id | thread_id 是任务编号（存档文件名），不是权限；谁能批准、批的是哪版补丁仍要在入口校验 |
| 恢复 | `graph.invoke(Command(resume=...), config)`；不能重发原始消息；`get_state().next` 为空说明没在等待 |
| 循环 | 回边就是普通边；节点写状态、路由读状态、计数器增长后不再选回边 |
| 业务预算 ≠ recursion_limit | 后者是框架安全阀（抛 GraphRecursionError），业务要自己写"最多修订/回滚几次、超限去 finalize" |
| 循环里的局部变量 | cursor 只在 return 时写回 State，恢复重跑读到旧值 → 得到同一目标阶段（前提仍是 interrupt 前无副作用） |
| 可视化 | draw_mermaid（先落 .mmd）、stream_mode="updates"（interrupt 输出为 `__interrupt__`）、StateSnapshot 的 values/next/tasks |
| 三个工程坑 | 恢复重跑审批节点导致副作用重复；复用旧 checkpoint/thread_id 污染测试；async def 里做阻塞 I/O 卡事件循环（同步短操作用普通 def） |
| 六阶段搭建 | P1 主线最短路 → P2 条件路由 → P3 ToolNode 并行 → P4 interrupt 审批 → P5 循环与预算 → P6 调试可视化；每阶段只叠加一种机制 |
| 变更分级与审批规则 | 含 patch_diff/auth/payment/password/token 判 H，len(diff)>800 判 M，其余 L；L 自动、M 级 INT-1 等 Tech Lead、H 级 INT-2A 等 Tech Lead + INT-2B 等安全负责人；任一拒绝 → finalize |
| 分支汇合 | 多条边指向同一节点即汇合；ToolNode 的并行汇合是"一个节点内部并发"，图上仍是普通节点 |
| 回滚重试当前阶段 | canary_cursor 1/2/3 对应 10%/50%/100%；回滚把游标减 1，下一圈再加 1 回到同一档，并追加 rolled_back:<stage> |
| langgraph dev | 读 langgraph.json 找图入口并注入内存 checkpointer；studio_graph.py 调 build_graph(None)，核心图代码不变 |

## 四、Harness 专题（重点）

### 4.1 定义与定位

> **Agent = Model + Harness。**
> Model 提供理解、推理、生成；Harness 是**围绕模型组织工具、状态、上下文和执行环境的支撑程序**，负责把输出接到真实执行过程。

它回答的不是"模型聪明不聪明"，而是这四个问题：

1. 它跑的是不是**要求的**测试？
2. 测试通过以后，有没有**再次修改**代码？
3. 中途等待过审批，执行时用的还是不是**批准过的**补丁？
4. 运行被打断，恢复后会不会**把已经完成的修改再做一遍**？

同一个模型接入不同 Harness，效果差距可以很大：失败时只返回"执行失败"，模型会反复改无关代码；返回失败用例、断言差异和代码位置，模型才知道哪条行为没满足。

### 4.2 六模块分工与"检查放在哪里"

| 模块 | 职责 |
|---|---|
| Tool | 提供读取、补丁、测试等具体能力 |
| Tool Runtime | 检查调用，管理执行，记录并返回结果 |
| Loop | 组织模型与工具之间的多轮交互 |
| State | 保存计划、执行事实、验证证据和未完成事项 |
| Sandbox | 限制实际操作能触及的文件、进程和网络 |
| 任务运行层 | 协调启动、等待、取消、恢复和收尾 |

**分工决定检查位置**（这是 Harness 的第一原则）：

- "这个路径是否允许写入"要放在**实际执行入口**——只放 Loop 的某个分支，换条调用路径就漏。
- "收到结果后是否继续请求模型"属于**运行控制**，不能由补丁工具自己决定。

### 4.3 核心机制：同一结果的两类去向

| 去向 | 用途 | 缺失后果 |
|---|---|---|
| 返回给模型 | 看到失败用例、断言差异，决定下一步 | 下一轮缺少修正依据，反复乱改 |
| 更新业务状态 | 记录证据，更新计划与完成检查 | 业务状态没变，程序仍可能允许交付 |

**分工的精确表述**：状态保存"程序需要核对的事实"，上下文提供"模型本轮需要的信息"。模型可以只看到简短测试摘要，程序仍保留完整测试记录。

**这就是 Harness 的中心命题**：同一事实必须正确进入 **模型 / 状态 / 审批 / 完成检查** 四个位置，且指向同一版本。

### 4.4 正常路径：从修复要求到交付（五步闭环）

| 步骤 | 关键动作 | 判据/坑 |
|---|---|---|
| ① 把"修好了"变成可检查行为 | 缺陷在 `isSessionExpired` 只比较 UTC 日期；要求覆盖 到期前/恰好到期/到期后/同日已超时 | 只说"把日期比较改成时间比较"不足以验收；完成契约不代替断言审查（测试漏了同日问题，记录齐全也不算修好） |
| ② 准备工作区 | 记录已有改动与允许修改范围；确认测试目录、运行时、依赖、后台服务；显式传工作目录，不依赖上次 `cd`；首轮上下文四项：目标 / 入口 / 边界 / 验收 | 塞入整个仓库；结束时分不清哪些是用户原有改动 |
| ③ 先确认失败，再应用补丁 | 读实现与调用方（保留真实路径、行号、片段）→ 跑复现测试 → 补丁经 Runtime 检查后在 Sandbox 写入 | 若复现测试通过，先查用例是否绕开问题，**不要立即修改**；所有写入入口都要检查（通用命令会绕过补丁工具）；补丁匹配失败要给具体原因并让模型重读，不能自动挑相似位置 |
| ④ 让测试结果决定下一步 | 先类型/语法/Lint，再三组：target / boundary / regression；失败分层：依赖缺失（记"尚未验证代码行为"）/ 断言失败（回传用例、预期、实际、日志位置）/ 超时 | 只跑最容易的一组；用 Git 提交号关联受测版本（Agent 改动通常未提交，要用工作区版本或**内容指纹**） |
| ⑤ 核对最终 Diff 再宣布完成 | 看源码/测试/配置：修复了到期逻辑、保留原鉴权、没有删用例/放宽断言/跳过检查、未越界；随后完成契约核对当前版本 Diff + 三组通过记录 + 交付产物 | 退出码为 0 只是执行证据，不能回答"需求有没有满足" |

**交付说明四问**：改了什么？实际验证了什么？哪些没有验证？还有什么限制？

### 4.5 异常路径：让继续执行有依据（五条规则）

1. **先确认动作有没有发生**，再决定要不要重试。
   | 发生了什么 | 处理 |
   |---|---|
   | 临时模型故障 | 按调用层规则有限重试 |
   | 补丁明确未匹配/未写入 | 返回原因，模型读取后调整 |
   | 缺少授权 | 保存待批动作，进入等待 |
   | 写操作结果不明 | 查执行记录与现场 |
   | 相同动作持续失败无进展 | 达限停止，保留未完成事项 |

   错误信息必须让**下一次动作发生变化**："修改失败"无用；"目标文件存在但待替换片段未匹配，请重新读取当前内容"才有用。

2. **写操作结果不明不能直接重放**：三种核对结论——已确认完整执行（恢复真实结果，不重复改）／确认未执行（满足条件再执行）／部分执行或仍不确定（保留未决，核查或交人）。**不能因为文件里出现了某段预期代码就认定整个动作成功**（多文件补丁可能只完成一部分）。

3. **取消要停到真实执行层**：任务入口 → 模型请求与 Runtime → 实际执行器 → 确认进程退出。取消不撤销已写入内容；进程是否退出不明时，不能立刻对同一工作区启动下一次运行。

   两个停止语义必须区分：`--pause-after` 保存后停止、任务保留 `running`、可恢复；`SIGINT`/ABORTED 把当前 runner 转为 `cancelled` 终态，不能都叫"可恢复暂停"。

4. **恢复前重新检查旧结论**：当前工作区是否变化？未决动作执行到哪？旧测试与待批动作是否仍适用？**检查必须发生在重新请求模型和执行工具之前**；不受影响的步骤可保留有效证据，只重检变化涉及部分。

5. **没有进展就停止**：比较工具名、参数、结果，再结合代码变化与计划推进；模型输出新解释 ≠ 有进展；局部重试成功不能清零任务总预算；停止后保存已有修改、测试结果、未决动作与停止原因（不依赖模型生成总结）。

### 4.6 完成检查的三条不变式（最容易被做错）

| 不变式 | 说明 | 对应反例 |
|---|---|---|
| **看当前版本** | 完成契约从证据里按 `artifactVersion === revision` 过滤，而不是听模型最终回复 | 只跑 target 也算完成 |
| **看内容而非计数器** | 版本号经过受控补丁才推进；同一次运行中文件被外部编辑，计数不一定变 → 用文件摘要核对受控范围（源码/测试/配置）与当前内容 | "版本 r1 没变，内容却变了" |
| **看最新结果** | 同一范围按时间取最新有效结果；最新失败不能被更早的成功掩盖；交付文档要检查"文件是否存在、是否含要求内容" | 早先 boundary 通过，掩盖后来 boundary 失败 |

一句话：**完成判断依据当前可以核对的事实，不依据历史上曾经发生过一次成功。**

### 4.7 接进 pi 的两个易错点

1. **首轮与后续轮分别准备**：首轮输入由应用构建，不能指望 `prepareNextTurn` 补上；完成判断要读最新业务状态。
2. **不是所有调用都经过 `afterToolCall`**：工具不存在、参数校验失败、`beforeToolCall` 拒绝时可能直接生成结果并跳过执行；只把拒绝记录写在 `afterToolCall` 会漏记。
   （审批同理：模型生成 `approved: true` 不会获得授权。）

### 4.8 不用 pi 时，手写 Harness 要补的五件事

| 要点 | 做法 |
|---|---|
| ToolOutcome 双读者 | `result_text`→模型；`events`→宿主；`is_error`→双方；`blocked`→宿主（被哪道门禁拦下） |
| 调用与结果精确配对 | 用**原 tool_call_id** 构造 tool_result；一次多调用要分别配对；收尾时对未配对的 tool_use 按"已有真实结果/确实被打断"区分 |
| 请求组装与轮次上限 | system 分稳定块+每轮块，缓存断点打在稳定块末尾；发送历史副本；`range(max_iterations+1)` 多出的一轮用于强制收尾；`stop_reason=end_turn` 只表示这一轮结束；`tool_choice` 不同缓存断点位置不同；强制文本轮只允许自然语言，参数未完整通过检查的调用不得提前分发 |
| 先暂存，再由宿主批准 | 检查顺序：变更 ID 是否在本会话来源记录 → 暂存内容是否符合当前护栏（读 `state.seen_changes`，不读本次传参）→ 是否需批准及是否已记录；批准标记先写→执行→无论成败撤销 |
| 宿主批准仍走同一执行器 | 批准按钮若绕过门禁直连后端，模型路径上的规则就没覆盖全部写入入口 |
| 防重复写入 ≠ 恢复回执 | 第二次被拒"已应用"能防重写，但不能把第一次的完整结果交还调用方；结果不明先核查副作用 |

### 4.9 三层验收：证明"连接"真的有效

| 层级 | 做法 | 能证明 / 不能证明 |
|---|---|---|
| ① 固定动作（脚本化模型） | 查：暂停是否留下可读 Checkpoint；恢复是否保留计划/记录/进度；已完成修改是否被重复执行；最终状态是否与完成检查一致 | 证明机制在固定输入下正确；**不能**证明真实模型能定位缺陷 |
| ② 真实模型跑登录任务 | 跑前记录工作区已有改动；跑后核对：实际 Diff、三组测试记录、交付文件、测试后是否又有相关修改；未执行的检查记"未执行"，环境问题记"尚未验证" | 证明端到端闭环；单次成功不等于稳定成功率 |
| ③ 主动制造反例 | 测试通过后再改文件（旧证据失效）／同范围先通后败（最新失败不被掩盖）／待批期间改目标文件（旧批准不可用）／运行中取消（进程真退出且进度被保存）／模型说"已完成"（缺证据不能绕过契约） | 证明约束不是摆设；只查日志里有没有"拒绝"不够，要查实际后果 |

**出问题时的定位表（找"第一个断开的连接"）**

| 现象 | 优先检查 |
|---|---|
| 模型没收到失败信息 | Runtime 返回 → 工具适配 → 消息回写 |
| 失败已进状态，任务仍完成 | 证据筛选 → 完成契约 |
| 取消后进程仍在 | AbortSignal 传播 → 实际执行器 |
| 恢复后重复写入 | 现场核对 → 未决动作处理 |

修复后：先重跑暴露问题的场景，再检查受影响的相邻行为。

### 4.10 Harness 与其余六节的关系（一句话版）

- **Loop 给它动力**：没有 Loop，Harness 只是单次调用外壳。
- **Planning 给它"账本"**：没有计划步骤，Harness 无法判断"缺哪一项"。
- **State/Checkpoint 给它"记忆"**：没有存档，Harness 的恢复分支无从下手。
- **Sandbox 给它"笼子"**：Harness 决定"要不要放行"，Sandbox 决定"放行后能碰到什么"。
- **Harness 给它们"接线"**：同一结果同时进模型与状态；同一版本同时被证据与完成检查引用。
- **LangGraph 给它"骨架"**：当流程需要跨进程等待人工时，审批闸门与 Checkpoint 由图承载，Harness 负责把业务事实接进节点。

                                              ▼

                                     │批准            │

                              │                          │
                              └──────────┬───────────────┘
                                         ▼
                              [完成检查] 当前版本？内容一致？最新结果？
                                    │                    │

                                    │                    │

                                    │

**三个"同一"贯穿全图**：

1. 同一次调用 —— toolCallId 在模型消息、证据、审计、审批四处一致。
2. 同一个版本 —— 证据、Diff、完成检查都指向当前内容（版本号 + 内容指纹）。
3. 同一个事实 —— 模型看到的失败与状态记录的失败是同一份，不是两套说法。

## 六、十条通用判据（可直接拿来做 Code Review 清单）

1. **能继续 ≠ 能恢复**：会话恢复只还原对话，业务恢复要还原计划、证据、工作区版本、审批与预算。
2. **拦截必须发生在副作用之前**：证据是 handler 调用次数为 0，不是"返回了错误"。
3. **完成必须看当前版本的最新证据**：旧通过不能证明新代码；最新失败不能被旧成功掩盖。
4. **结果不明不得重放**：先查执行记录与现场，再分"已执行/未执行/不确定"。
5. **审批绑定具体操作**：批准后仍要复核补丁、目标文件、权限与有效期；一张审批单只被执行一次。
6. **检查和授权要放在执行入口**：散在分支里的检查，换条路径就漏。
7. **专用工具优先于通用 Shell**：能力越宽，边界越难守。
8. **默认拒绝 + 越界可感知**：静默失败会让模型反复重试，也让事后无法追溯。
9. **业务预算独立于框架安全阀**：`maxTurns` / `maxRevisions` / `recursion_limit` 三者语义不同，不可互替。
10. **先找第一个断开的连接，再改提示词**：按 输入→上下文→决策→校验→审批→沙箱→执行→回写→状态→完成→恢复 逐段验证。

## 七、高频易混对照表

| 容易混为一谈 | 实际区别 |
|---|---|
| Turn vs Run | Turn = 一次模型响应（含 0~N 个工具调用）；Run = 整个任务执行 |
| 任务内循环 vs 任务外循环 | 前者是一次 Run 内怎么继续；后者是什么事件触发一次 Run |
| ReAct vs Plan-and-Execute | "这一步往哪走" vs "整体怎么走"，可嵌套 |
| 计划 vs Workflow | 步骤由模型临时定 = 计划；步骤由工程师预先写好 = Workflow |
| 改参数 vs 修订计划 | 目标步骤未变 = 改参数；方向/依赖/交付路径变 = 修订 |
| skipped vs completed | 跳过没有完成证据，尤其验证步骤不能算通过 |
| 工具失败 vs 任务失败 | 前者可重试或换路径；只有达停止条件才是任务 failed |
| 暂停 vs 取消 | 暂停 = running + INTERRUPTED，可续；取消 = cancelled 终态 |
| 会话恢复 vs 业务恢复 | 前者还原"聊过什么"，后者还原"哪一步可信、哪次写入不明" |
| Checkpoint vs 审计 | 恢复依据 vs 事实与判定留痕；用 runId + toolCallId 关联 |
| Trace vs Checkpoint | 记录发生过什么 vs 保存接下来怎么继续 |
| 中断 vs 回滚 | 中断只停止，不撤销已写入内容 |
| interrupt "暂停" vs 重跑节点 | LangGraph 保存 State 不保存调用栈，恢复会从节点开头重跑 |
| recursion_limit vs 业务预算 | 框架安全阀抛异常 vs 业务自己路由到 finalize/incomplete |
| 工具执行成功 vs 测试通过 | 拿到失败日志也是"成功获得结果"，代码仍未修好 |
| 测试通过 vs 当前代码已验证 | 通过后代码又变了，旧结果只证明修改前状态 |
| 审批通过 vs 已应用 | 批准只授权，执行结果另行核对 |
| 防重复写入 vs 恢复回执 | 防重写不等于把第一次结果交还调用方 |
| 路径合法 vs 落点合法 | resolve 后仍可能有软链越界，需 realpath/禁链 |
| steering vs followUp | 当前轮的安全边界注入 vs 循环准备停止时接着处理 |
| 格式版本 vs 代码版本 | 存档结构版本 vs 工作区内容版本 |
| 工具批次 terminate | 整批最终结果都终止才提前结束，不是单个说了算 |

## 八、复习自测（按章末 20 题压缩为 8 组）

1. Loop 成立的最小证据是什么？（Tool Result 真实进入下一轮且 ID 匹配）
2. 模型说"完成"后，系统凭什么放行？（完成契约 + 当前版本证据 + 交付物）

4. 什么情况必须修订计划？（证据推翻根因、依赖或交付路径变化；修订不得降低标准）

6. 结果不明时为什么不能重放？（可能已成功、只是回执丢了）
7. Harness 的核心是什么？（同一事实正确进入模型/状态/审批/完成检查）
8. 发现 Agent 有问题，第一步做什么？（沿主链找第一个断开的连接，用确定性反例证明修复）

# 《第一章 学习笔记》知识点梳理与逻辑框架

> **一句话总纲**：LLM 负责不确定性决策，工程系统负责确定性边界。
> 全章不是在教"怎么写一个 Agent 框架"，而是在教"如何为 Agent 划定可信边界，并证明边界有效"。

## 1. 总体逻辑框架

### 1.1 三层认知结构

| 层次 | 回答的问题 | 对应模块 |
|---|---|---|
| **认知层（为什么）** | Agent 由哪些层组成？每层为什么存在？ | 1.1 |
| **能力层（怎么做）** | 一次模型调用、一次流、一段 Prompt、一份输出、一次网关调用，各自的主链和边界是什么？ | 1.2 ~ 1.6 |
| **工程层（怎么落地）** | 如何把原型变成可配置、可部署、可测试、可治理的服务？ | 1.7 |

### 1.2 五层能力演进（1.1 的核心骨架）

| 层 | 回答的工程问题 | 关键概念 | 缺了它会怎样 |
|---|---|---|---|
| **Prompt** | 模型应该按什么角色、目标、约束行动？ | 岗位说明书、行为规范 | 模型不知道何时该调工具、不能验收 |
| **Context** | 这一轮模型到底看到了什么？ | System/User/Assistant/Tool Result、任务目标、历史压缩 | 模型"失忆"，重复提问、基于错误信息决策 |
| **Harness** | 这一次 Run 带着什么模型、Prompt、Context、Tools、策略开始？ | 模型选择、工具发现、身份权限、Hooks、取消、Trace | 装配逻辑散落在 `main.py`，系统不可维护 |
| **Loop** | Tool 结果回来之后怎么办？何时继续、何时停？ | 观察 → 决策 → 行动、回填 Context、终止条件 | 只能做单步工具调用，无法完成长任务 |
| **Graph** | 哪些流程应显式建模为状态与控制流？ | Node/Edge、fake-edge test、diamond、Verifier | 可并行的任务被串行化，缺少独立验证 |

> 说明：五层是**教学分层**，不是行业官方"五代 Agent"；成熟 Agent 往往同时具备五类能力。

### 1.3 七个模块的依赖关系

```
1.1（总图/术语/四项能力）
   └─ 1.2（模型调用与输入输出边界）——所有后续能力的物理底座
        ├─ 1.3（Streaming）——把"一次性结果"扩展为"持续事件"
        ├─ 1.4（Prompt）——决定模型的行为倾向（软约束）
        └─ 1.5（Structured Output）——决定输出能否被程序消费（硬协议）
                └─ 1.6（LLM Gateway）——把 1.2~1.5 收口成唯一调用入口
                        └─ 1.7（服务化）——把 1.6 原型变成可部署、可治理的服务
```

**依赖关系的三个要点：**

1. **1.2 是地基**：Tool Runtime、Loop、Harness 全部建立在"输入输出边界"之上；这一层不清，错误会静默流入后续循环。
2. **1.4 与 1.5 是一对**：Prompt 负责"让模型倾向正确"，Structured Output 负责"让结果可拒绝"。前者是软引导，后者是硬协议，不能互相替代。
3. **1.6/1.7 是收口**：把散落在每个 Agent 里的模型调用、密钥、重试、成本口径、Prompt 版本，收敛为一个平台边界。

## 2. 分模块知识点与重要环节

### 2.1 1.1 从 LLM 到 Agent：全章地图

**核心命题**：Agent 的价值不在"会调用工具"，而在"模型之外的确定性边界"。

**学习姿态（三条"不要求"与七条"必须"）**

- **不要求**：脱离 AI 默写 Agent 框架；背 Codex / Pi / LangGraph 的全部 API；记类名、字段名和源码目录。
- **必须**：解释组件为何存在；画出它在整个运行链中的位置；按接口补出关键骨架；审查 AI 生成的实现；发现职责、状态与可信边界问题；用测试、Trace 和错误分析验证；把一种设计迁移到新业务场景。
- **角色切换**：从"依赖 AI 给答案"升级为"我给 AI 工程规格，我来判断什么是正确答案"；四步是理解设计理由 → 自己定义边界与正确性 → 让 AI 提高实现效率 → 用测试与错误分析验证。
- **反例（执行顺序错误无法撤销）**：先 `tool.handler(call.arguments)` 再 `has_permission(tool.name)`。即使返回 `PERMISSION_DENIED`，退款已打款、文件已删除、数据库已写入、邮件已发送，错误响应无法撤销已发生的副作用。

**主链**

```
用户输入 → LLM 决策 → Tool Call（候选动作） → Runtime 受控执行
        → Tool Result 回填 Context → 再次调用 LLM → … → 最终答案 / 系统终止
```

**重要环节**

| 环节 | 要点 | 工程含义 |
|---|---|---|
| **Agent 的最粗定义** | `Agent = LLM + Tool`；由 LLM 驱动、能调用外部工具、并基于结果继续推理 | LLM 本质只做"输入上下文 → 预测下一段 Token"，没有外部世界的手脚 |
| **Function Calling 的真正变化** | 从 `输入 → LLM → 文本` 变为 `输入 → LLM → 动作请求 → 外部系统 → 真实结果 → LLM` | 模型第一次从"决定下一句话"变成"决定下一步做什么" |
| **Tool Call 的性质** | 只是模型提出的**候选动作**，不表示函数已执行 | 执行权必须留在 Runtime |
| **单次调用 → 多轮循环** | 有分支、有依赖的任务需要"观察 → 决策 → 行动"反复 | 这是 Loop 出现的原因 |
| **五层能力** | Prompt / Context / Harness / Loop / Graph | 每层都为解决上一层的工程问题而出现 |
| **Harness vs Tool Runtime** | Harness 回答"这次 Run 带什么开始"；Runtime 回答"这次 Tool Call 能否执行、怎么执行、失败怎么办" | 两者最易混淆，必须分清 |
| **Harness 装配清单** | 选模型、加载 System Prompt 与项目规则、恢复 Session、构造本轮 Context、发现可用 Tools、安装 Hooks、注入可信身份、加载权限策略、创建取消信号、启动 Loop、记录 Trace | Harness 是"运行前的装配者"，不是执行者 |
| **Tool Runtime 主链** | `ToolDefinition → active tools → 冻结 ToolSnapshot → 模型看到 Tool Schema → Tool Call → prepare → execute → finalize → ToolResultMessage` | 注册、快照、参数校验、权限、超时、重试、审计都在 Runtime |
| **Context 的核心判断** | 模型能力 ≠ Agent 能力；模型只能依据"这一轮看到的 Context"判断，Context 给错，模型照样做错 | 这是 Context Engineering 存在的理由 |
| **Graph 的判据** | `fake-edge test`：这一步真的需要上一步的结果吗？ | 找不到两条无依赖任务，就不该建图，仍是 Loop |
| **Graph 的灵魂** | Verifier 必须独立、上下文干净，只看到"发现"本身 | 不能让做事的 Agent 检查自己，否则只是"自我点头" |

**Graph 的两个关键结构与适用边界**

- **diamond 模式**：Fan out（并行派出多个 worker，各处理一个独立角度）→ Reduce（用普通代码合并、去重、过滤，不消耗模型 token）→ Synthesize（用一个 Agent 基于合并结果撰写最终答案）。
- **验证节点**：独立 Verifier 的唯一任务是"尝试杀死"前一个节点的发现，存活才传递、否则丢弃；它的上下文必须干净，只看到"发现"本身；通常并行跑正确性、时效性、来源真实性三个角度。
- **不该用 Graph**：任务小而孤立（协调开销大于收益）、需要逐步人工审批、探索性任务（方向随时会变）、步骤强依赖（找不到两个无依赖任务，那就是 Loop）。

**最小 Agent Loop 的五个检查点（全章反复复用）**

1. 模型只提出候选动作（拿不到 handler）。
2. Loop 判断继续还是结束，且必须有**模型之外**的终止条件。
3. 所有 Tool Call 都进入 Runtime，不能在 Loop 里写巨大 `if/else`。
4. Tool Result 必须写回 Context，并保留 `tool_call_id`——**结果不是最终答案，而是下一轮决策的输入**。
5. Loop 必须有确定性运行上限（`max_turns`、超时、预算、取消、死循环检测）。

**框架观察窗口**

| 框架 | 观察重点 | 一句话结论 |
|---|---|---|
| Pi | 轻量 Agent Loop 与 Harness 骨架 | 模型只看到工具协议与 Schema，看不到 handler；真正执行发生在运行侧；`ToolResult` 带 `toolCallId` 回流下一轮；生命周期含 `beforeToolCall / afterToolCall` |
| Codex | 生产级 Tool 执行与安全边界 | 模型提议，系统裁决：执行前要回答"允许吗、在哪个 Sandbox、能访问哪些路径、能否写文件/访问网络、是否需人工 Approval、被拒怎么办、失败能否 Retry" |
| Claude Code | 成熟 Harness 的装配能力 | 项目规则、Context 管理、Tools、Hooks、Permissions、Session、Subagents、Skills，以及 Context Compaction |
| LangGraph | State 与显式 Graph 编排 | 把隐式 Loop 变成可观察、可暂停、可恢复、可回放的对象 |

> **模型能力决定下限，Harness 设计决定上限。**

**四项能力（全章的价值主张）**

1. 构建并**验证** Agent 工具运行时（不是"能跑一次"）。
2. 软件工程判断：契约、职责、可信边界、状态一致性、失败语义、取舍。
3. 与编程智能体协作：我给工程规格，AI 加速实现，责任仍在我。
4. 决定构建方向：要不要 Agent、要不要 LLM 决策、Tool 该多粗、MVP 要什么。

**从最小 Loop 到生产级的差距**：还差 System Prompt、Context Builder、Tool Registry / Snapshot、参数校验、ExecutionContext、权限、Approval、Hooks、Sandbox、Cancellation、Streaming、Checkpoint、Trace、Memory、Planning、Subagent、Graph、Eval 等能力。但这些能力不是"越多越高级"，而要按业务复杂度、运行时长和风险选择。

**六阶段学习路线**：模型调用 → Tool Runtime → Agent Loop / Harness → Context、Memory、RAG → Multi-Agent / Eval → Production Ready。本章只覆盖第一阶段及其工程化前提。

> 两句原话值得记住：**Agent 工程是判断与取舍，不是组件收集**；**可靠的 Agent 不是保证模型不犯错，而是保证模型犯错后，动作停在正确的位置。**

**与其他模块的关系**：1.1 提供"地图与术语"；后续每一节都是把总图中的某一块放大——1.2/1.3 放大"模型调用"，1.4 放大"行为约束"，1.5 放大"输出校验"，1.6/1.7 放大"运行装配中的模型端口"。

### 2.2 1.2 从模型 API 到可控输入输出

**核心命题**：模型返回的是**候选内容**，不是可信系统状态。一次调用必须有目标、上下文、输出契约、失败边界。

**主链**

```
任务目标与可信上下文
  → Model Adapter 组装请求
  → 模型返回候选输出 / 结构化事件
  → Schema 与业务规则校验
  → ModelResult（成功/失败、错误码、是否可重试、trace_id）
  → 交给 Loop
```

**重要环节**

| 环节 | 关键知识点 | 易错点 |
|---|---|---|
| **API 形态** | Chat Completions：兼容最广的消息基线；Responses：更贴近 Agent 的 item / 事件 / 工具 / 多模态语义 | 把业务 Loop 绑死在某一接口上 |
| **参数观** | `temperature/top_p` 是采样分布调节，`max_tokens` 是输出预算，都不是"质量旋钮"；参数需在入口做范围校验（`temperature ∈ [0,2]`、`top_p ∈ (0,1]`、`max_tokens > 0`） | 答得不好先盲调参，而不是检查输入与任务边界；reasoning 模式可能忽略 `temperature/top_p`，参数应属于 Provider 能力配置 |
| **上下文预算** | 三份预算：① 系统指令与可信规则 ② 当前任务证据 ③ 模型输出空间 | 把聊天记录、文档、工具结果无限塞入 |
| **截断处理** | 先分类为"输出预算不足/停止原因异常"，再缩上下文、提预算、拆任务 | 直接 `json.loads` 后重试，把预算问题误判为格式问题 |
| **输出协议** | JSON（能解析）→ JSON Schema（长什么样）→ Pydantic（程序如何验收）→ 原生 Structured Output（生成时约束） | 认为"返回 JSON = 业务正确" |
| **结构 vs 内容** | 结构检查（字段/类型/枚举）+ 内容检查（业务规则/证据支撑） | 把权限、身份、审批状态、DB 主键交给模型生成 |
| **失败分层** | 请求前 / 传输中 / 服务端 / 生成后 / 解析后，各自策略不同 | `except Exception: retry()` 一把抓 |
| **Model Adapter** | Loop 只依赖稳定契约：输入消息、成功与否、错误码与可重试性、trace_id；Adapter 还统一 `usage`、`finish_reason`、供应商请求 ID | Loop 直接依赖供应商 SDK，换模型就要改循环 |

**失败阶段与策略（本节最重要的一张表）**

| 阶段 | 典型故障 | 后果 | 正确策略 |
|---|---|---|---|
| 请求前 | 认证失败、参数非法 | 必然失败 | 立即终止，报警/修配置 |
| 传输中 | 超时、临时网络错误 | 不知是否收到 | 有限重试 + 指数退避 + jitter |
| 服务端 | 限流、过载 | 放大雪崩 | 尊重 `Retry-After`，退避或切只读备用模型 |
| 生成后 | 拒答、截断 | 不能安全继续 | 终止或转人工；截断先修预算 |
| 解析后 | 格式/结构错误 | 不能驱动 Loop | 一次定向纠错；仍失败则结构化返回 |

> **两个容易漏掉的重试边界**
> - 重试只能包裹**无副作用**的模型请求；写工具的重试另有幂等、审批与补偿语义，混成一个 `retry()` 会制造重复下单、重复建单。
> - 解析后的错误只做**一次**定向纠错，仍失败则结构化返回，不能把格式问题混进网络重试。

> **核心原则**：重试不是盲目重来，而是**有分类、有预算、有终止语义**的有限恢复。

**与前后关系**：本节建立"一次性调用"的输入输出边界；1.3 把同一条边界从"一次性结果"扩展为"持续事件"，控制点、错误分类、契约与 Adapter 抽象都不变。

### 2.3 1.3 Streaming：把长任务变成可观察、可取消、可恢复的事件流

**核心命题**：Streaming 改善**感知延迟**与**过程可见性**，不会让模型推理更快，也不会自动保存事件、停止后台任务或恢复崩溃。

**三个指标（必须分清）**

| 指标 | 含义 | 主要影响因素 |
|---|---|---|
| TTFT | 请求开始 → 第一个可显示 Token | 排队、网络、输入长度、Prefill |
| 生成耗时 | 首 Token → 输出结束 | 输出长度、解码速度 |
| 端到端耗时 | 用户发起 → Run 最终完成 | 模型 + 多轮 Loop + 工具 + 存储 |

**主链（正向 + 反向）**

```
Client 创建 Run
  → Agent Loop 请求 Model Adapter
  → Provider chunk → ModelStreamEvent（Adapter 归一化）
  → Agent Loop → RunEvent（run_id + seq）
  → Event Store 按 run_id + seq 保存
  → SSE Gateway 编码并推送
  → Client 增量解码 → 切 frame → 去重 → 节流渲染

反向：Client 取消 → POST /runs/{id}/cancel → Loop 在安全点检查 → 关闭模型流/停止工具
      → 保存部分结果 → 唯一 run.cancelled
```

**六个阶段与关键边界**

| 阶段 | 做什么 | 不可省略的边界 |
|---|---|---|
| ① 消费模型流 | Adapter 把供应商 chunk 归一化为内部事件（`text.delta` / `finish_reason` / `usage`） | 不把供应商 chunk 直接给前端；TTFT 记在首个**非空** `text.delta`，不能记在"连接成功"或"收到第一个 chunk" |
| ② 定义 RunEvent | 模型事件 → 运行事件 | 模型事件≠运行事件；`run_id + seq` 用于去重、续传、Trace；**唯一终态**（completed/failed/cancelled 三选一） |
| ③ SSE Gateway | 编码 `event/data/id` + 空行 + 心跳 | 创建 Run 与订阅 Run 分离；断线只中断订阅，不等于取消；警惕伪流式与 Nginx/CDN/压缩层缓冲；响应头需 `Cache-Control: no-cache, no-transform` 与 `X-Accel-Buffering: no` |
| ④ Client | 增量解码 → 按空行切 frame → 按类型分发 | 一次 `read()` ≠ 一条事件；UTF-8 可能跨包；按 `seq` 去重，不比较文本；渲染节流 |
| ⑤ 取消 | 停止后台任务、释放资源 | 关闭连接 ≠ 停止生成；`cancelling` 表示正在收口，`cancelled` 才是终态；部分输出可保留但不可自动提交 |
| ⑥ 失败与恢复 | 按失败阶段决定重试/重放/查状态 | 流前可重试；已出文本不重跑拼接；工具已开始先查工具状态；终态后只重放不重跑；`Last-Event-ID` + Event Store；长文本用 checkpoint 分节 |

**四个易混概念**

- **Streaming**：逐步传输已产生的内容和状态。
- **Cancellation**：停止仍在运行的模型或工具。
- **Event Replay**：断线后重新发送已发生的事件（通知可以丢，事实事件不能丢）。
- **Checkpoint**：Worker 崩溃后恢复任务执行状态。

**三种"重试/恢复"动作不能互相替代**

| 动作 | 含义 | 适用场景 |
|---|---|---|
| Model Retry | 重新推理 | 建流前、未产生业务事件时的瞬时故障 |
| Transport Replay | 重发已保存的事件 | 客户端断线后按 `Last-Event-ID` 续传 |
| Task Resume | 从 Checkpoint 继续任务 | Worker 崩溃、任务被中断 |

> 断线续传依赖 Event Store：Redis Pub/Sub 只能通知"有新事件"，订阅者离线期间消息会丢——**通知可以丢，事实事件不能丢**。

**上线前必测九项**：拆包（任意拆分仍能还原）、粘包（一次读取多条 frame 不丢）、Unicode（中文跨字节边界）、顺序与去重（`seq` 单调、重放不重复渲染）、取消（后台任务退出且只有一个 `cancelled`）、竞态（`completed` 与 `cancelled` 不能同时成立）、流前失败（允许有限重试）、流中失败（不重新生成后拼接）、重连（从 `Last-Event-ID` 继续同一个 Run）。

**伪流式的六类隐患**：收完整答案后一次 `yield`；前端依赖某供应商 chunk；断线后模型仍在生成并计费；点停止只关界面没停后台 Run；流中断后重新请求并把两段文本拼接；缺少终态事件。

**与前后关系**：1.2 解决"拿到一个可信结果"；1.3 解决"过程可观察、可取消、可恢复"；两者共用 Adapter、错误分类和契约思想。1.6 的流式网关直接复用本节的 SSE、终态与取消语义。

### 2.4 1.4 Prompt Engineering：把业务意图写成行为契约

**核心命题**：Prompt 负责**影响模型怎样理解和生成**；程序负责**决定哪些结果可以接受、哪些动作允许发生**。软约束与硬边界不能互换。

**主线**

```
定义岗位 → 校准边界（Few-shot） → 组织任务（拆解） → 工程化管理（模板 / 防注入 / 版本）
```

**四个阶段的要点**

| 阶段 | 解决的问题 | 关键做法 | 验收标准 |
|---|---|---|---|
| **① 定义岗位** | Agent 是谁、为谁解决什么、依据什么、不能做什么、怎么表达 | System Prompt 五要素：角色 / 目标 / 证据 / 边界 / 输出 | 行为约束必须**可观察**、**有故障含义** |
| **② 校准边界** | 抽象规则说不清（如"什么算紧急"） | 2—3 个示例：典型正常 + 边界 + 拒绝/信息不足 | 示例覆盖不同路径，且判断依据符合业务 |
| **③ 组织任务** | 一次调用做不完、步骤有数据依赖 | 拆成"分析 → 处理 → 检查"三阶段，定义输入/输出/禁止事项 | 每阶段只消费**已存在**的证据，不引入新事实 |
| **④ 工程化管理** | 文本散落、易被注入、无法回滚 | 模板化 + 三层防注入 + 版本与回归 | 变量缺失在调用前失败；攻击路径无副作用 |

**模板化的四个工程判断**

1. 规则与运行时数据分离（用户消息不拼进 System Prompt）。
2. 变量是显式契约：缺失与多余的变量都在模型请求前失败，而不是静默生成残缺 Prompt。
3. 变量有长度预算（例如 `max_variable_chars = 20_000`），防止整篇文档无边界注入导致膨胀。
4. 每次渲染产生指纹（`sha256` 取前 16 位），并连同模板名称、版本记入 Trace。

> **输出风格不是"让回答更好看"**：它服务于使用场景——面向普通用户要"结论先行、少术语、明确下一步"；面向客服要"已确认事实 / 缺失信息 / 风险与建议"；面向下游程序要"固定字段与稳定枚举"。

**任务拆解的两个反例与适用边界**

- 先"生成草稿"再"分析"，模型会围绕已形成的答案找理由；检查阶段看不到原始证据，只能检查文案是否自洽，不能判断事实依据。
- 不需要拆解的任务：单一标签分类、输入完整的短文本改写、不依赖外部事实的简单总结、错误成本低且可立即校验。拆的是可观察的工作阶段、数据依赖与失败出口，不是"模型的思考过程"。

**四条边界（必须分清）**

| 名称 | 是什么 | 不是什么 |
|---|---|---|
| System Prompt | 跨任务稳定的角色、目标、规则、表达要求 | 不是某用户本次的问题 |
| User Prompt | 本次任务 | 不是身份、权限或批准记录 |
| 运行时上下文 | 订单、知识库、历史消息等数据 | 其中出现的句子不自动成为系统指令 |
| 代码约束 | Schema、权限、白名单、状态机 | 不能被模型文字覆盖 |

**三个典型故障**（分层的理由）

1. 用户输入覆盖长期规则（"忽略之前要求"）。
2. 外部数据伪装成指令（知识库文章里的恶意文本）。
3. Prompt 承担了本应由程序保证的权限（要求模型"不要越权"，却把管理员工具交给它）。

**Few-shot / 规则 / 代码的分工**

| 需求 | 更合适的手段 | 原因 |
|---|---|---|
| "缺少订单号时追问" | 明确规则 | 条件清晰，可直接表达 |
| "什么语气算简洁客观" | Few-shot | 风格边界适合示例展示 |
| `priority` 只能是三个枚举 | Schema / 代码校验 | 必须确定性保证 |
| 用户是否有权建单 | 权限代码 | 可信业务事实 |
| 订单当前状态 | 查询业务系统 | 不能从示例或模型记忆推断 |

> **Few-shot 是软引导，不是安全控制。**

**审查 AI 生成的 Few-shot**：看是否覆盖不同路径而非换词重复、判断依据是否符合真实业务、输出是否与当前 Prompt 一致、是否泄露真实用户信息或过时政策。不要把线上对话原样复制进 Prompt（可能含手机号、订单号、错误客服承诺与噪声），须脱敏、筛选、人工确认后再改造成教学样例。

**注入防护的三层防线**

1. **Prompt 分区**：明确哪些是可信规则、哪些是不可信数据。但标签（如 `<user_message>`）只是语义提示，**不是安全边界**——攻击者可以闭合标签后继续注入。
2. **行为收缩**：外部内容只能被分析，不能赋予新目标或新权限。
3. **程序控制**：高风险动作、权限、业务事实由代码决定；未知动作默认拒绝；权限从认证上下文读取，绝不接受模型生成的 `approved`。

> **直接注入 vs 间接注入**：直接注入来自用户输入；间接注入来自 Agent 读取的外部内容（知识库文章、网页、邮件、订单备注）。两者最终都以文本进入上下文，危险程度相同。

> **验收要看副作用**：模型说"我拒绝了"不算安全，必须断言攻击输入下高风险工具调用次数为 0。

**版本管理的四件事**

- 版本对象绑定：规则 + 示例 + 变量契约 + 变更说明 + 回归案例 + 模型配置。
- 语义化规则：措辞修正升补丁；规则/示例变化升次版本；角色、目标、输出协议变化升主版本。
- 回归四类案例：**正常 / 边界 / 失败 / 攻击**，并验证副作用而非只比文字。
- 审查 AI 修改 Prompt：先看四类变化，再比文字流畅度——角色与目标是否变、证据来源与冲突优先级是否变、禁止事项与完成条件是否变、Few-shot 是否改变模型偏向。

**与前后关系**：1.2 定义"模型能看到什么"；1.4 定义"模型应该怎样做"；1.5 定义"模型输出怎样被验收"。三者合起来才是完整的"输入—行为—输出"控制面。

### 2.5 1.5 Structured Output：把模型输出变成可验证的业务协议

**核心命题**：Prompt 只能约束"倾向"，协议才能保证"可消费"。自由文本必须收敛为**字段明确、类型稳定、可以拒绝**的业务对象。

**主线**

```
业务消费方 → 定义协议（Pydantic）→ 生成 JSON Schema → 模型生成
          → 服务端校验 → 定向修复 → 缓存降级 / 明确失败 → 下游
```

**五层概念的分工**

| 层次 | 解决 | 不解决 |
|---|---|---|
| JSON | 能否按语法解析 | 字段、类型、取值 |
| JSON Schema | 字段、类型、必填、枚举、额外字段 | 业务含义 |
| Pydantic | 定义类型、生成 Schema、校验、反序列化 | 业务规则本身由谁定 |
| 原生 Structured Output | 生成阶段按 Schema 约束 | 事实正确、业务决策正确 |
| 服务端校验 | 统一验收不同 Provider 的返回 | 后续权限与业务策略 |

> JSON 解决"能不能解析"，Schema 解决"长什么样"，Pydantic 解决"程序怎样定义和验收"，业务代码解决"这个结果能不能用"。

**为什么不能用自然语言、关键词或正则**：它们没有稳定边界，容易误判且**不报错**——`"暂时不要转交"` 仍含"转交"；模型把"转交"改成"分派"就漏检；更危险的是解析器选错分支却不报错。而 `{"action":"route","team":123}` 能被 `json.loads()` 解析，仍不符合系统协议。

**Pydantic 的四项职责与三个必要配置**

- 职责：定义类型、生成 JSON Schema、校验数据、反序列化为 Python 对象；`model_json_schema()` 发给模型，`model_validate_json()` 校验返回，协议只有一份来源。
- 配置：`extra="forbid"`、`strict=True`、枚举用 `Literal`；跨字段关系用 `model_validator(mode="after")`。
- 注意：`model_validator` 的业务关系不一定能完整投影成 JSON Schema，所以"给模型 Schema"只能减少格式错误，服务端仍须对最终对象做一次完整校验。

**五个阶段**

| 阶段 | 关键动作 | 关键判断 |
|---|---|---|
| ① 定义协议 | 从**消费方**出发设计字段（工单场景仅 `action / summary / team / question`） | 不要 `model_thought`；字段名面向业务，不面向模型思考过程 |
| ② 约束生成 | 优先原生 Structured Output，不支持则 JSON + 本地校验 | 原生只保证结构，不保证完成、拒答、业务组合、事实、下游权限 |
| ③ 校验返回 | 三层错误：JSON 语法 / 字段结构 / 业务组合 | 错误归一化为 `issues`（路径 + 错误码 + 消息）；**全有或全无**，不给默认值兜底 |
| ④ 纠错重试 | 反馈"哪里错、只修协议、只返 JSON" | 修复循环五检查点：同 Schema、每次重校验、只返合法对象、带错误反馈、有最大次数（`max_repairs=2` → 总 3 次） |
| ⑤ 失败收口 | `ok / degraded / failed` 三态 | `failed` 时 `decision` 必须为空；缓存需同输入哈希、同协议版本、在有效期内、历史已通过校验并再次校验 |

**哪些错误该给模型，哪些不该**

| 失败类型 | 正确处理 | 原因 |
|---|---|---|
| 字段缺失、类型错误、枚举错误 | 反馈给模型修复 | 模型能重组输出 |
| 跨字段组合冲突 | 反馈给模型修复 | 模型能补齐或清空字段 |
| 网络超时、限流 | Provider 调用层退避重试 | 模型修不了网络 |
| 认证失败 | 立即失败并修配置 | 重复生成不会恢复凭证 |
| 业务权限不足 | 交给业务策略 | 模型不能扩大用户权限 |

**失败收口的两个硬约束**

- **缓存的业务禁区**：快速变化的订单状态、价格、权限判断与任何写操作，都不能因"结构合法"就复用旧结果；无法确认时效时，正确做法是返回 `failed` 转人工，而不是为可用性牺牲正确性。
- **只捕获 `StructuredOutputFailure`**：程序 Bug、数据库故障不能被伪装成"输出格式问题"。

**校验边界必测四类样本**：`invalid_json`、未知动作、`invalid_combination`、`valid`；并用副作用计数器证明 `failed` 时下游消费次数为 0。

**与前后关系**：1.4 管"行为倾向"，1.5 管"输出契约"；1.6 的 Gateway 把"结构化请求 → 校验 → 错误码"收进统一调用链，1.7 再加"两层保证"（供应商生成约束 + 本地校验）。

### 2.6 1.6 LLM Gateway：把模型调用收口成统一入口

**核心命题**：Gateway 不是"多转发一次 HTTP"，而是把模型调用变成**统一、可校验、可降级、可观测**的平台能力。

**主链（一条时间线）**

```
FastAPI 入口：请求校验（统一契约、extra=forbid；stream + response_schema 在入口直接拒绝）
  → Prompt 装配：模板名 + 版本 + 变量（缺变量在调用前失败）
  → 模型路由：白名单 + 能力检查（逻辑模型名 → 真实模型/地址/密钥/能力）
  → Provider 调用（普通 / 流式，SDK 差异被隔离）
  → 普通响应：JSON 解析 + Schema 校验
     流式响应：增量文本 → SSE 事件（不缓存完整答案）
  → 临时故障：有限重试（明确异常白名单）
  → 能力等价 fallback（首块之后不切换）
  → CallTrace：模型 / Prompt / Token / 成本 / 延迟 / attempts
```

**三个 ID 不能混用**

- `request_id` 标识一次 Gateway 模型调用。
- `trace_id` 标识一次 Agent Run，可包含多轮模型与工具调用；一次 Run 可能有十次 Gateway 请求，所以不能用 `request_id` 代替 `trace_id`。
- `business_id`（工单号、订单号）只用于查询领域对象，不能拿来关联模型调用。

**五个必须守住的边界**

| 边界 | 要回答的问题 | 典型失守 |
|---|---|---|
| **Contract** | Gateway 是否定义了自己的请求、响应、错误协议？ | 直接透传供应商 payload，表面统一 URL，实际没统一契约 |
| **Prompt** | 调用能否还原为"哪个模板 + 哪个版本 + 什么变量"？ | 调用方直接上传完整 System Prompt，绕过版本与审查 |
| **Provider** | 换供应商是否需要改路由、Trace、Loop？ | SDK Response 泄漏到上层，业务代码依赖 `choices/chunk` |
| **Execution** | 普通与流式是否走同一条受控路径？ | CLI、测试、线上各调一套，重试与 Trace 三份不一致 |
| **Trace** | 一次失败能否回答"请求了谁、切到了谁、几次、多久、哪个模板、什么错误"？ | 只写一句"模型调用失败" |

**工程判断清单**

- **逻辑模型名 ≠ 供应商模型名**：上层只认稳定别名，部署时才解析真实模型。
- **能力是 fallback 的资格**：备用模型必须满足本次请求的全部能力，否则只是把基础设施故障变成协议故障。
- **关闭 SDK 内部重试**：`attempts` 必须对应真实上游调用数，预算才可控。
- **流式成功不能只看连接关闭**：只有收到完成事件才算成功；流中错误必须成为流协议的一部分。
- **Gateway 重试 ≠ Loop 重试**：前者输入/模板/Schema/目标不变；后者可能补上下文、改计划、换工具。
- **流式 fallback 以"是否已输出"为界**：首块前可切；首块后停流并报错，不能换模型续写拼接。
- **API Key 只留在 Gateway**：Agent 不持有供应商密钥，轮换、切换、审计都在一个边界完成。
- **重试白名单要显式列出**：连接失败、超时、限流可有限重试；认证/配置错误、未知模型、Prompt 模板缺失、非法 JSON、Schema 失败都不走网络重试。
- **重试预算的真实算术**：每个候选最多尝试两次；若 Gateway 最多 4 次、外层 Loop 又重试 3 轮，一步任务最坏可产生 12 次模型调用——`attempts` 必须对应真实上游调用数，Harness 必须读取它并把调用纳入任务级预算。
- **Structured Output 的两种发送方式**：`json_schema` 把 Schema 作为 API 原生约束（`strict=True`）；`json_object` 只保证 JSON 格式，Schema 靠 Prompt 传递。两者都必须再过本地 `json.loads + jsonschema.validate` 才算通过。

**MVP 最小闭环**：统一请求与响应、模型白名单、Provider Adapter、Prompt 版本、普通调用、Streaming、结构化输出返回后校验、有限重试、能力等价 fallback、稳定错误码与 Trace。缺少任何一项，主链都会断开。

**本节明确不扩展**：复杂路由 DSL、熔断器集群、全链路 OpenTelemetry、跨区域容灾、计费对账平台——先把契约、唯一 Provider 入口、校验、重试、fallback 与 Trace 做真实。

**与前后关系**：本节把 1.2（契约与失败分类）、1.3（SSE/终态/取消）、1.4（Prompt 版本）、1.5（Schema 校验）合成一个入口；1.7 再把它拆成可部署的服务，并为 Harness 提供稳定的 `ModelPort`。

### 2.7 1.7 项目演进：从单文件原型到可部署的统一模型调用服务

**核心命题**：不是推翻 1.6 重写，而是把已验证的"模型执行边界"从单文件原型升级为**可配置、可部署、可测试、可治理**的独立服务。

**为什么要演进**：多个 Agent、多个调用方、多个供应商接入后，单文件原型会遇到——模型与价格写死在代码里、调用记录只在进程内存、Prompt 不能独立发版、鉴权限流健康检查缺失、每个 Agent 各自保存密钥与重试策略。

**六个"各自调模型"的后果**（统一 Gateway 的真正理由）

1. 同一个 429 在不同项目用不同重试策略。
2. 同一个模型费用在不同团队用不同计算口径。
3. 模型下线要改多个 Agent。
4. Prompt、模型、参数无法组成可回放版本。
5. 安全审计无法回答某次输出发给了哪个端点。
6. Eval 与生产走过不同代码路径。

**LLM 调用的"四层成功"**

| 层级 | 成功条件 | 失败示例 |
|---|---|---|
| 传输层 | HTTP 请求完整返回 | DNS、超时、连接中断 |
| 服务层 | 供应商接受并执行 | 429、5xx、认证失败 |
| 协议层 | 响应能映射到内部协议 | 缺 choice、未知事件 |
| 业务层 | 输出满足 Schema 与业务规则 | JSON 合法但工具参数越权 |

> 只检查 HTTP 200，会漏掉后面三层。

**服务化后的主链**

```
请求 → API Layer（鉴权 / 限流 / 输入校验 / SSE 出口）
     → 规范化 ModelRequest（租户、trace、逻辑模型、输出协议）
     → 冻结（freeze）Prompt / Schema / 预算 / Trace 版本
     → Prompt 解析（Bundle：模板 + 变量 + 版本）
     → Registry / Router（能力过滤 → 预算/区域/数据策略 → 健康 → 评分 + 理由）
     → Adapter（内部协议 ⇄ Provider 协议）
     → 普通结果校验 / 统一事件流
     → Retry → Fallback / 熔断
     → Trace + Cost Ledger → 返回 Agent Loop
```

**七个阶段的关键点**

| 阶段 | 关键知识点 |
|---|---|
| ① 统一协议 | OpenAI Compatible 是**对外接口形态**，在 API Layer 终止；内部用自己的 `ModelRequest / ModelResponse / ModelEvent / GatewayError`；错误也必须是协议 |
| ② 统一入口 | 兼容 ≠ 复制全部字段；只支持平台治理过的子集，未知字段立即拒绝；身份必须来自认证中间件，不接受 body 自报 `tenant_id`；禁止透明代理 |
| ③ 发现与路由 | 能力注册表（streaming / json_object / json_schema / tool_calling / vision / context 上限）；路由四步：逻辑模型 → 能力过滤 → 预算/区域/数据策略/健康 → 评分排序并记录理由；Fallback 有明确适用与不适用清单；新端点上线前必须在固定 Eval 集比较 |
| ④ 执行与收敛 | 普通、流式、结构化输出走**同一条编排链**，差异只在结果消费；流式必须唯一终态；SO 两层保证（供应商约束 + 本地校验）；半个 JSON 到达时绝不执行工具；修复调用计入同一 Run 与预算，新 `call_id` 关联原调用，有最大次数 |
| ⑤ Prompt 装配 | Prompt 是可发布、可复现、可评估的**行为契约**：模板 + 输入 Schema + 输出 Schema + Few-shot + 工具版本 + 默认模型 + Context 预算 + Eval 集 + content hash；`StrictUndefined` 缺变量即失败；版本固定到 `RunState`；灰度按租户/用户/Run 稳定，同一 Run 不换版本 |
| ⑥ 证据回写 | Trace 九维：关联 / 路由 / Prompt / 用量 / 延迟 / 弹性 / 结果 / 错误 / 成本；延迟**六段**拆分（排队、Prompt 渲染、路由、连接、TTFT、生成）；TTFT 以首个有业务意义的 delta 为准；成本用**版本化价格表**；高基数字段（user_id、run_id、prompt_text）不做 Metrics Label |
| ⑦ 失败治理 | 按生命周期**十阶段**分级（认证 / 请求校验 / Prompt 渲染 / 能力路由 / 排队 / 建立连接 / 等待首 Token / 持续生成 / 输出校验 / 记账）；错误归一化；重试由次数 + 总截止时间 + 错误类型共同约束；流式首 Token 是重试边界；**并发限制比 QPS 更重要**；Backpressure 不能丢终态、错误、usage、工具事件；幂等键不能假设供应商不会重复计费 |

> **重试默认值（可照抄的工程口径）**：`max_attempts=3`（1—5）、`base_delay=0.25s`、`max_delay=2.0s`；`delay = uniform(0, min(base·2^(n-1), max))`；若退避时间 ≥ 剩余 deadline，立即返回 `TIMEOUT`（504，不可重试）。
>
> **并发限制至少四层**：全局并发、每供应商并发、每租户 QPS + 并发、每模型 Token/分钟。只限 QPS 挡不住长请求造成的连接堆积。
>
> **幂等键的边界**：同一幂等键若请求指纹不同必须拒绝，不能返回旧结果；除非供应商给同等保证，否则不能假设端点不会执行两次。

**接回 Harness 的约定与 Gateway 边界**

- Loop 只依赖 `ModelPort`，不知道供应商、SDK、重试次数、价格表。
- `trace_id → run_id → step_id → call_id / tool_call_id` 是完整追踪链。
- 预算必须从 Run 传播到 Call；Gateway 的重试与 fallback 消耗上层 Run 的剩余预算。
- **Gateway 不负责**：任务业务终态、工具副作用、权限扩大、长期记忆、代替 Harness 判断任务完成。

**Run 预算必须向下传播**：`RunBudget` 至少含 `max_steps`、`max_model_calls`、`max_total_tokens`、`max_cost_usd`、`deadline_at`；每次调用由 `derive_call_budget` 取 `max_output_tokens = min(2000, remaining_tokens)` 并继承剩余成本与 deadline。否则单次调用都不超预算，整个 Run 却可能无限消耗。

**六类测试**：Adapter Contract、Router、重试、Streaming、Structured Output、可观测性。关键断言包括：不可重试错误只调用一次；429 在预算内重试；退避超 deadline 立即终止；SDK 内部重试被禁用；每次 attempt 都写 Trace；首个 delta 后不透明切换；`completed / failed / cancelled` 只出现一个；`attempts` 与真实调用次数一致；日志不含 API Key、完整 Prompt 与堆栈。

**新候选上线前的 Eval 七指标**：任务成功率、Structured Output 合法率、工具选择正确率、平均 Loop Step、P50/P95 TTFT 与总延迟、Token 与成本、拒答与安全行为。

**1.7 刻意保留的两个边界**：限流与熔断是单进程内存实现，多副本部署需迁移到 Redis 等共享存储；服务不维护 Agent Run 状态、不替 Harness 判断任务完成。

**项目实战七轮扩展**：内部协议 + Fake Adapter → 真实 Adapter → Streaming 与取消 → Structured Output → 路由与 Fallback → Prompt Bundle → 资源治理与观测闭环。

**验收不变量（摘要）**：Agent 侧不导入供应商 SDK；OpenAI 客户端可直接调用 `/v1/chat/completions`；不支持的能力在调用前失败；路由理由可查；首 Token 前可重试/切换、之后不拼接；取消只产生一个终态；JSON 合法但业务不合法不进 Loop；Prompt 缺变量在调用前失败；每次调用可定位 Prompt / Schema / 路由 / 模型 / 价格版本与尝试次数；日志不含 API Key 且默认不记录完整敏感 Prompt；Token/Cost/TTFT 可按租户/模型/Prompt 版本聚合；重试、fallback、修复调用受同一 Run 预算约束；Fake Adapter 能稳定复现成功、限流、超时、流中断与非法输出。

**迁移验收**：换 Provider 不是复制 Adapter，须重新决定支持哪些能力、参数名/事件类型/`finish_reason`/错误码如何映射、哪些错误可重试与 `Retry-After` 是否可信、价格与 Token 口径、能否进入当前候选集与 fallback 顺序。

**与前后关系**：1.7 是本章终点，也是下一章的起点——它交出的是一个"模型执行基础设施"，而 Agent Loop / Harness 才在此之上决定任务如何推进。

## 4. 易混概念速查表

| 概念对 | 区别 |
|---|---|
| Function Calling vs Agent Loop | 前者解决"模型怎样表达调用意图"；后者解决"结果回来之后怎么办、何时停" |
| Harness vs Tool Runtime | Harness 管"这次 Run 带什么开始"；Runtime 管"这一次 Tool Call 能否执行、怎么失败" |

| Streaming vs Cancellation vs Replay vs Checkpoint | 传内容 / 停任务 / 补发事件 / 恢复状态 |
| Token vs chunk vs ModelStreamEvent vs RunEvent vs SSE frame | 计费单位 / SDK 增量 / 归一化模型事件 / 运行事实 / 传输帧，不是一一对应 |
| JSON vs JSON Schema vs Pydantic vs 原生 SO | 能解析 / 描述形状 / 程序验收 / 生成时约束 |
| Gateway vs Router vs Adapter vs Provider | 统一入口 / 选端点 / 协议翻译 / 实际服务方 |
| Retry vs Fallback | 同一候选的瞬时故障恢复 vs 切换能力等价候选 |
| TTFT vs 生成耗时 vs 端到端 | 首字可见 / 解码速度 / 整个 Run |
| `cancelling` vs `cancelled` | 正在收口 / 已确认终止 |

## 6. 十条可复用的工程原则

1. **LLM 负责不确定性决策，工程系统负责确定性边界。**
2. **模型输出只是候选**，必须校验后才能进入下游。
3. **Tool Call 不是执行许可证**，参数必须验证、执行必须受控。
4. **错误必须分类**：先判断发生在哪个阶段，再决定重试、修复、降级还是终止。
5. **所有重试都要有预算**：次数、总截止时间、错误白名单、退避与 jitter。
6. **已产生副作用或已输出文本，不做透明重来。**
7. **一个 Run 只有一个终态**；流停止不等于任务成功。
8. **协议单一来源**：同一份 Pydantic Model 同时生成 Schema 与做验收。
9. **可复现才算可运维**：版本 + hash + trace + 版本化价格表。
10. **先画边界、再写伪代码、再给 AI 规格、最后自己故障注入。**

## 8. 一页记忆卡

```
Agent = LLM + Tool                         （起点，太粗）
     + Prompt     → 行为倾向
     + Context    → 这一轮看到什么
     + Harness    → 这次 Run 怎么装配
     + Loop       → 结果回来怎么办、何时停
     + Graph      → 哪些流程显式化、可并行

一次调用：目标 → 上下文 → 输出契约 → 失败边界 → ModelResult

一份输出：消费方 → Pydantic → Schema → 生成 → 校验 → 修复 → 降级/失败
一个网关：契约 → Prompt → 路由 → Provider → 校验/流 → 重试/fallback → Trace
一个服务：API → 规范化 → 装配 → 路由 → 执行 → 收敛 → 观测；四层成功才算成功
```
